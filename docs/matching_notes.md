# Matching Notes

Compiler/linker behavior and techniques learned while matching functions in this game. Helpful to review when a function is stuck short of 100%. Functions that are stuck for now live in [`nonmatching.md`](nonmatching.md).

Each entry is a reusable rule: what you see (symptom), why, and what to write instead. Function names and addresses are examples of where it applied.

---

## Compiler gotchas

### GX setters: three source-shape levers

Scope: found on `Dolphin/gx` (`GC/1.2.5n`); untested on game code. For a GX setter whose instruction sequence is identical but registers/scheduling differ, sweep `{macro, declare-at-address} x {plain, const} x {gx local, direct}` before anything else.

- **`extern __GXDataStruct* const __GXData;`** Without `const`, a late extra `lwz rX,-11608(r13)` appears or `gx` lands a register too high (MWCC assumes stores may alias the pointer). Highest yield.
- **Direct `__GXData->field` over a `gx` local**, once `const` is in. Keep a local only where the original really reloads (`GXCopyDisp`/`GXCopyTex` use both).
- **`volatile GXFifoObj GXWGFifo : 0xCC008000;`** instead of the cast macro. It changes scheduling, not just addressing, and is per-function (`GXSetTevOrder` prefers the macro, `__GXSetViewport` needs the declare-at-address form). Tell: a `lwz rX,__GXData` reload that the original schedules above the FIFO `stb`/`stw` and ours leaves below them, with registers otherwise identical, needs the declare-at-address form (`GXSetProjection`, `0x8018FF90`).

Smaller findings:

- **`u32 c = *(u32*)&color;`** for a by-value `GXColor` (`GXSetTevKColor`). Declare it at its point of use: an inline `*(u32*)&color` hoists the `rlwimi` early (`GXSetFog`). Mask every byte field even when the shift already narrows it (`(c >> 24) & 0xFF`, `c & 0xFF`, `(c >> 8) & 0xFF`): the mask emits nothing, but without it `GXSetTevColor` gets an extra `addi rX,rY,0` accumulator copy after the first `rlwimi` and hoists the second register's setup. `GXSetTevKColor` matches with or without the masks.
- **A separate `srawi` before an `rlwimi rX,rY,0,...` where the original folds the shift into the insert (`rlwimi rX,rY,31,22,31`): the `>> 1` is signed.** Cast before shifting, `x = (u32)(x_off + 342) >> 1;`, then insert `x`. `(u32)((x_off + 342) >> 1)` still shifts signed (`GXSetScissorBoxOffset`, `0x80190398`).
- **C around an inlined `asm {}` helper lands in shifted registers (and the original's `stwu` to the FIFO comes out as `stw` plus `addi rX,rY,-0x8000`): the helper's temps are `register` locals, not hard-coded registers.** Declare `register u32 zero, color; register f32 a0_a1, ...;` in the `static inline` and name them in the asm; MWCC then allocates them (to the original's r0/r6/f5-f0) and colours the caller around them. With `r0`/`r6` written literally the caller's chain moves off r0 (`GXLoadLightObjImm`, `0x8018D8D4`, the later SDK's `PushLight`).
- **`phyAddr = (u32)dest & 0x3FFFFFFF;` temp** in `GXCopyDisp`/`GXCopyTex`. The mask emits nothing, but inlining `(u32)dest >> 5` changes the code.
- **`u8` for `GXBool` params** even when only forwarded (`GXSetCoPlanar`). If register allocation is off in a tiny setter, try the narrower param type (`GXSetDither`, `GXSetColorUpdate`, `GXSetAlphaUpdate`).
- **Named local for a compound `__rlwimi`** (`GXSetCullMode` `hwMode`), else it lands in `r0`.
- **`fcmpu` operand order follows source order:** `(lbl_80670770 == ptr[0])` matched `GXSetProjectionv`.
- **A local for a reused masked param moves its register, and its slot in the declaration list matters:** `u32 f = format & 0xF;` declared *first* in `GXInitTexObj`.
- **A bare `cntlzw` feeding a one-bit `rlwimi` is a folded `==`:** `x == n` compiles to `subfic`/`cntlzw`/`srwi 5`, and MWCC absorbs that `>> 5` into the insert's rotate (rotate = field shift + 5). Write the comparison at the *unfolded* shift: `SET_REG_FIELD(reg, 1, 11, type == 3)` emits `rlwimi rX,rY,6,20,20`. Hand-writing `__cntlzw(3 - type)` gets the instructions but not the scheduling (`GXSetBlendMode`).
- **To stop MWCC sharing `base + i * 4` between two pointers into one table, give each its own byte-offset base:** `(u32*)(base + 20) + i` and `(u32*)(base + 60) + i` off a `u8* base` local are reassociated only *after* CSE, so each gets its own `add` plus a folded `addi`. `&tbl[0][i]` / `&tbl[1][i]` yields one CSE temp and a copy. The `u8*` local also hoists the `lis`/`addi` above the branch (`GXSetTevOp`).
- **Float constants in an FP-heavy function must be real literals, not `extern const f32`:** an extern loads into a scratch and copies out twice (`lfs f0`; `fmr f3,f0`; `fmr f31,f0`), or, with no copies, shifts the FP allocation (ours spills into f10/f11 where the original stops at f9 and reloads a constant late into a freed register); a literal loads straight into the first destination. Claim the unit's `.sdata2` literal range in `splits.txt` (shrink dtk's merged literal symbol at the claim's end in `symbols.txt`), plus `#pragma force_active on` (below). MWCC orders the pool by pre-scheduling code order, in which a loop body precedes its condition (`GXSetFog`). A pooled `0.5` feeding `fmuls` can be `/ 2.0f` in the source: `* 0.5f` gives the same instructions but different scheduling (`__GXSetViewport`, `0x80190248`).
- **Two functions sharing one `.sdata2` pool are one translation unit:** if a split-off function fails to bake with `Symbol '@NN' is in .sdata2, but unit ... has no .sdata2 split`, its literals (float constants, the int-to-float magic double, const-initialised `GXColor` locals) are pooled with a neighbour's. Merge the two into one unit and claim the whole pool (`__GXInitGX` joins `GXInit`; even the `__GXData` pointer lives in that pool, defined as a `const` pointer to its `.bss` object).
- **Hoist a shared table base by declaring its pointer local first:** `u8* tbl = lbl_XXXX;` as the *first* local put the `lis`/`addi` in r31 before the first call and reused it for several `tbl + off` arguments (`__GXInitGX`). Any later slot gives a different register assignment.
- **A `.bss` base the original computes *before* a leading call and keeps in a saved register (`lis r4`/`addi r31,Packet@l` ahead of `bl OSRegisterVersion`, `SIInit`): use a `u8*` local cast from a struct-array extern, and write byte-offset stores.** `SIPacket* p = Packet;` with `p[i].chan` leaves the `lis`/`addi` after the call in a scratch register. `unsigned char* base = (unsigned char*)Packet;` (with `extern SIPacket Packet[4];`) plus `*(s32*)base = *(s32*)(base + 0x20) = *(s32*)(base + 0x40) = *(s32*)(base + 0x60) = -1;` hoists it. Declaring the extern as `unsigned char Packet[]` loses the hoist again. The chain evaluates right to left, so write it in ascending order to get the original's `0x60, 0x40, 0x20, 0x0` stores. For a single struct pointer (`fp = &FatalParam`, extern here but `static` in the SDK TU), assigning the local on the line *before* the leading call is enough (`Halt`, `0x804027E0`).
- **FP code where the original does one `fdivs f,1.0,x` and then only `fmuls` by it (three results sharing one divisor), and ours emits a divide per result plus an extra `-1.0` literal: the SDK source is `d = 1.0f / x;` then `a * d`.** MWCC never turns `a / x` into a reciprocal multiply. Also `fnmsubs` where the original has `fmuls` + `fsubs` means `#pragma fp_contract off`. When only the FP register numbers differ in one arm of a `switch`, permute the order of its independent result assignments (3! builds; the original order was `a0, a1, a2`) (`GXInitLightSpot`, `0x8018D70C`, whose `.data` jump table and 11 `.sdata2` literals are claimed with `#pragma force_active on`).
- **`OSSetGbsMode` (`0x8017FACC`) is asm; plain C stalls.** The original's frame is `-0x20` (the `LockSram` inline pair does not add the extra 8 bytes here), and the `(mode & 0x7C00) == 0x5000` / `(mode & 0xC0) == 0xC0` tests compile to `cmplwi` on a `u16` operand with a separate hoisted `clrlwi r4,r3,16`. An unsigned mask now gives that `cmplwi` (next entry), so only the frame is unexplained for a C retry.
- **`cmpwi` where the original has `cmplwi` after masking a `u16`/`u8` field: make the mask constant unsigned.** The field promotes to `int`, so `(x & 0x7C00) == 0x5000` compares signed; `(x & 0x7C00u) == 0x5000` gives `cmplwi` with no other change (`UnlockSram`, `0x8017F2E4`).
- **Stack slot order follows declaration order in reverse for aggregates:** the earlier-declared local gets the higher offset. In `__GXInitGX`, declaring `texObj` before `identity_mtx` put the matrix at the lower slot, as the original has it.
- **A `u8` parameter on the callee adds a `clrlwi` after a ternary argument:** if the original passes the `li 1`/`li 0` result straight through, prototype the parameter as `u32` (`GXSetFieldMode`'s second argument).
- **The original reloads a pointer field (`lwz r4,0(rX)` for a branchy ternary argument, then `lwz r9,0(rX)` again for the remaining arguments) where ours loads it once: obtain the base pointer from the SDK accessor the original inlined, written as a real function in the same unit.** MWCC's CSE across the ternary's basic blocks depends on how the base was produced; an inlined call's result blocks it, a plain expression doesn't. A local holding the compare's own operand (`TEXHeader* thp = tdp->textureHeader;` used only in the condition) works too, but the accessor is the SDK shape. Symptom in `tools/objdiff_mismatches.py`: a run of `DIFF_ARG_MISMATCH` register swaps plus one `DIFF_DELETE` load on the original side, at 100% fuzzy (`TEXGetGXTexObjFromPalette`, `0x80411418`, with `TEXGet` merged into its unit).
- **The original recomputes a value yours reuses (`clrlwi` repeated after a `switch` on the same mask): make the two expressions differ in type.** MWCC only CSEs identical IR, and the SDK often mixes a signed variable with a `(u32)` cast. `OSInit` declares `s32 consoleType`, switches on `consoleType & 0x0FFFFFFF` (`int`) and computes `tdev = (u32)consoleType & 0x0FFFFFFF` in the `default:`.
- **A zero-initialised static *array* (`static f32 ZeroPS[2] = { 0 };`) lands in `.sdata`, not `.sbss`:** scalars with `= 0` still go to `.sbss`, so only the aggregate moves, and every later `.sdata` literal shifts with it. Leave the array uninitialised.
- **MWCC pools each translation unit's `.data` -- strings *and* file statics -- into one object addressed from a single base register.** This is the default (ac-decomp disables it per-file with `-pool off`). The giveaway is a `lis`/`addi` pair that materializes one `.data` address into a saved register, followed by bare `addi rX, base, imm` with **no relocation** for every string and static in the unit. dtk merges the whole run into one `lbl_XXXXXXXX` object, so the pool boundary is also the TU boundary: anything reachable by immediate offset from that base belongs to the same source file.

  Consequences for matching:
  - **The pool's contents fix every offset**, so a function can only match once *all* of its TU's other pool users are in the same unit. Pulling one function out early gives the right instructions with the wrong immediates.
  - **Addresses materialized from the pool base are not hoisted out of loops**, because the `addi` is late address materialization rather than a frontend expression. Standing in for the pool with `extern u8 blob[]` plus explicit offsets *is* frontend arithmetic, so LICM lifts each `blob + off` into its own saved register, which grows the frame and renumbers every saved register. If a function is instruction-perfect but has extra hoisted `addi`s and an off-by-N `stmw`, look for a pool (`OSExceptionInit` matched once `OSInit` joined it in `OS.c` with real literals).
  - **Split dtk's pool blob into one `symbols.txt` entry per object, or identical instructions still diff.** objdiff's data-flow pass tags each `addi rX, base, off` with an `R_PPC_NONE` pseudo-relocation and only accepts it when symbol address *and* addend agree, so the target's `lbl_blob+0x11C` never equals your `@131+0`. One `lbl_<addr> ... scope:local data:string` per string (real names for tables) fixes it; the names don't matter, the addresses do.

- **`GXSetVtxDesc`/`GXSetVtxDescv` (`0x8018BF08`/`0x8018C174`): a `switch` over the vertex attribute with `SET_REG_FIELD` arms, plain u32 `attr` (numeric cases 0-10, 25 NBT, 11-20 CLR/TEX; cmplwi 0x19).** In `GXSetVtxDesc` the `type` param must be `int` (`cmpwi r4,0` for the `!= NONE` tests; `u32` gives `cmplwi`). In `GXSetVtxDescv` the loop needs a `static inline SETVCDATTR(GXAttr attr, GXAttrType type)` called as `SETVCDATTR(list->attr, list->type)`, with `GXAttr`/`GXAttrType` *enums* (and the list struct fields the same enums); `u32`/`int` params or locals let MWCC reuse the loop condition's `lwz`. Each jump table is 0x68 (8-aligned), so the units claim their table without merging.
- **Decode a jump table rather than trusting a reference decomp's case list:** this game's `__GXGetTexTileShift` uses `0x2B`/`0x2C` where ac-decomp has `0x24`/`0x25`.
- **A `switch` whose arms each assign to `*ptr` and `return` gets the store and `blr` tail-duplicated into every arm:** assign a local in the arms and store once after the switch, and the shared `b tail` comes back (`GXGetVtxAttrFmt`).
- **Dolphin SDK register writes use the CodeWarrior `__rlwimi` intrinsic, not plain C:**

  ```c
  #define SET_REG_FIELD(reg, size, shift, val)                    \
      (reg) = (u32)__rlwimi((int)(reg), (int)(val), (shift),      \
                            (32 - (shift) - (size)), (31 - (shift)))
  ```

  A bare `rlwimi` in the original is the giveaway. Plain C like `(reg & ~mask) | ((val & m) << shift)` or dropping the value mask does not match.

- **An `asm` function disables peephole optimization for every later function in the same translation unit** on GC/1.2.5n. Usual symptoms are lost displacement folding, lost record-form compares, and early returns turning into branches to the shared epilogue.

  The fix is adding `#pragma peephole on` immediately after the asm function closes. `#pragma scheduling on` is not needed. This matters in any unit that mixes an early asm function with later plain C, since address order often forces the asm function to appear first. Exception: when the original function *also* has peephole off (its real TU had an earlier asm function), keep it off, or `lis` hoists above the prologue (`__OSContextInit`).

- **CodeWarrior treats an undeclared data symbol in `asm` as a local label:** declaring the existing external object before the asm function is required for `@ha`/`@l` relocations to compile.
- **Raw words in MWCC `asm` (trailing zero padding, data-as-code): `opword 0`, not `.long`/`.4byte`** (`.long` gives `end of line expected`). `fn_80169AF4` (`0x80169AF4`) ends with four `opword 0`.
- **A zero word in `.text` that a `bl` targets is code, not padding: dtk calls it `pad_<addr>_text` and drops a `lbl_` there only because its analyzer rejects the invalid instruction and restarts the function at the next word.** Check a zero run against the dol's branch targets before absorbing it as trailing padding (rule above). `0x801796B4` was the dol's only one-word zero run and its only zero word that is a branch target: `fn_8017A608` calls it with `li r3,1` / `crclr 6` / `bl` and never restores its own lr, so the callee is a `noreturn` stub whose illegal word halts the CPU, followed by the `blr` GCC emitted as its epilogue. Give it one `type:function size:0x8` symbol and one unit (`Runtime.PPCEABI.H/fn_801796B4.c`: `nofralloc`, `opword 0`, `blr`), not a `lbl_` plus a separate 4-byte lone-`blr` unit. Two checks rule alignment padding out here: the neighbouring libgcc objects are **not** 8-aligned (`__lshrdi3` `0x801796BC`, `__moddi3` `0x801796FC`, `__umoddi3` `0x8017A134` all start 4-mod-8), and an object holding nothing but an unreferenced `blr` would never have been pulled out of a library archive. Merging the two also retires the `force_active` entry the lone `blr` needed: it was foldable only because nothing referenced it (129 lone-`blr` functions survive in the original dol, so mwld's original link did not fold them wholesale).
- **A branch into the middle of a data object (`b lbl_80573680+0x8708`) needs a symbol at its target: MWCC `asm` cannot write `b sym+addend`** (`illegal operand` / `end of line expected`, with or without parentheses or `bc`), and an `opword` leaves the original's `R_PPC_REL24` unmatched (99.89%). dtk rejects any symbol inside another, even `type:label size:0x0` (`overlaps with symbol`), so shrink the enclosing blob to end at the target, add a sized object there (`lbl_8057BD88`, `size:0x1F8`), declare it `void lbl_8057BD88(void);` and write `b lbl_8057BD88`. Then rebase every `src/` reference at or past the split onto the new symbol (`lbl_80573680+0x88E0` -> `lbl_8057BD88+0x1D8`); progress won't flag the ones you miss, but `tools/objdiff_mismatches.py` does (`fn_80169B48`, `0x80169B48`).
- **C that reaches a field more than 0x7FFF into a `.bss` blob (struct member or byte array) compiles to `lis sym@ha` / `addi` / `addis 1` / `stb -0x770f(rX)`; the original's `lis sym+0x88F1@ha` / `stb sym+0x88F1@l(rX)` (one `lis`, addend in the reloc) is not reachable from C.** Write the function as `nofralloc` asm with `(sym+off)@ha`/`@l` operands, as the disassembly prints them (`fn_8016C458`, `0x8016C458`; `fn_8016C3DC` too).
- **Hardware-register arrays must use CodeWarrior's declare-at-address form, not a pointer-cast macro:**

  ```c
  volatile u32 __SIRegs[0x100] : 0xCC006400;      /* correct */
  #define __SIRegs ((volatile u32*)0xCC006400)    /* compiles, does NOT match */
  ```

  The macro form folds the index into the base register (`mulli`/`addis`/`stw`) instead of the original separate-index `stwx` form. Reference decomps often carry the `#define` behind an `#ifdef __MWERKS__ ... #else`; that fallback is unwanted.

- **Operand order matters on carry ops:** `ticks + *timeAdjustAddr` compiles to `addc r30,r30,r4`, `*timeAdjustAddr + ticks` to `addc r30,r4,r30`. When a function is one instruction off, try reversing the expression first.
- **`mr. rD,rS` where the original has `cmpwi rS,0` then `addi rD,rS,0` (4 bytes longer): write the compare constant-first, `if (0 <= result)`.** `result >= 0` tests the copy, which the peephole folds into `mr.`; the later SDK's `0 <= result` tests the source (`CARDFastOpen`, `0x8040E1BC`, where `result` comes back from an inlined helper).
- **A `static` helper called from two sites gets inlined unless told otherwise:** if the original keeps the `bl` (function 0% match, prologue lacks `mflr`), wrap the helper in `#pragma dont_inline on` / `#pragma dont_inline reset` (`__GXSetSUTexRegs`).
- **A full-width `SET_REG_FIELD` (8-bit field at shift 0) loses the original's `clrrwi`, and a `u8` param adds a `clrlwi`:** use a `u32` param and write `__rlwimi((int)(reg & 0xFFFFFF00), (int)vol, 0, 24, 31)` explicitly (`AISetStreamVolLeft`).
- **A `clrlwi rX,r3,24` right after a `bl` that the original lacks means the callee's return type is too narrow:** declare the extern as returning `u32` (locals too), even if the real function returns `u8` (`AISetStreamPlayState`, which also uses `(reg & ~1) | state` and `(reg & ~0x20) | 0x20` in plain C where the original has `clrrwi`/`rlwinm` + `ori` instead of `rlwimi`).
- **`#pragma peephole off` fixes several distinct symptoms; try it early** (the original's state comes from an `asm` function earlier in its real translation unit, see above):
  - Redundant `b <next instruction>` branches at loop/branch join points (often two or three in a row, so translate them literally), plus a separate `cmplwi`/`blt` where ours folds the compare. In a loop-heavy function this restores many instructions at once (`GXInit`, six loops). A `static asm` stub at the top of the file produces byte-identical output, so prefer the pragma, which emits no extra function.
  - `stwu` before `mr r4,r3` (arg copy after frame setup) in a tiny wrapper (`OSRegisterVersion`). Default codegen emits the copy first; `scheduling off` alone misorders `li`/`crclr`.
  - `clrlwi` separate from a following `slwi` (indexing a table by a `u8` param), where ours emits a merged `clrlslwi` (`__OSSetExceptionHandler`/`__OSGetExceptionHandler`).
  - Early `return 0;` compiles to a bare `blr` where the original branches to the shared exit (`b .L_end`) in a tiny pointer-returning function. Restructuring into a single `r` result variable has no effect (`__GXDefaultTlutRegionCallback`).
  - A hardware-register read where the original keeps `lis`/`addi 0x3000`/`lwz 0x24(r3)` (base add not folded into the displacement), plus `cmpwi` and a `b` to a shared `blr`: use peephole off and a signed `int` for the flag. The declare-at-address `__PIRegs` form is still right (`OSGetResetCode`).
  - Two `b <next>` after an inlined `while (1) { ... break; }` read loop, plus `neg`/`cmpwi` where ours has `neg.` (an `s64 < const` test) and the frame-setup `cmpwi r3,0` sitting after `stw r31` rather than hoisted: all one cause. Put the pragma before the `static inline` helper so it also covers the caller (`__GXShutdown`, `0x801905A4`). Reshaping the loop (`do`/`for`/`goto`/nesting) never produces the `b`s.
  - Non-record `rlwinm`/`cmplwi` pairs and `extsb r3,r0` + separate `cmpwi r3,0` (`__OSCacheInit`, `stricmp`).
- **Align-up arithmetic gets reassociated (`add size, a` first) when written with plain `unsigned long` temps:** use the SDK's shape: a `ROUNDUP(x, a)` macro `(((unsigned long)(x) + (a)-1) & ~((a)-1))`, with `unsigned char*` locals for the pointer add (`(u8*)ptr + size`) (`OSAllocFromArenaLo`).
- **`base + (index << shift) + constant` written as an arithmetic expression (any grouping, any intermediate-variable split) always folds to `slwi` / `addi const` / `add base` (const before base); the original has `slwi` / `add base` / `addi const` (base before const):** write it as an array index through a cast instead: `((T (*)[1 << shift])(base + constant))[index]`. This makes the constant fold into the cast pointer and the index scale into the array subscript, producing base-then-constant in the right order. No amount of reordering the plain-arithmetic form (temp variables, statement order, operand order, `#pragma scheduling off`) changes the plain form's result (`__AXServiceVPB`, `0x804085F8`, `base + (index<<8) + 0x4D00` naming a 256-byte-stride array of a 0x4D00-byte-offset region).
- **Two pointers set up for an unrolled copy loop come out in swapped registers, the one derived from a now-dead parameter getting a fresh register (`addi r6,r3,0x34`) where the original reuses the parameter's in place (`addi r3,r3,0x34`): declare the loop counter inside the block.** `if (p->n != 0) { unsigned long count; ... for (count = p->n; count != 0; count--) *dst++ = *src++; }` matches; a function-scope counter breaks it even when only one loop uses it. Declaration or assignment order of the two pointers, `register`, and pointer types don't help (`__AXServiceVPB`, `0x804085F8`).
- **Loop tail emits `bne top; b exit` where ours emits `beq exit; b top`:** write the back-edge as `if (x != 0) { continue; } break;` instead of `if (x == 0) { break; }` (`OSCancelThread`'s inlined `UpdatePriority`).
- **A retry loop ending `cmplw rNew,rOld` / `mr rOld,rNew` / `bne top`, where ours adds an `addi rX,rOld,0` copy or ends `beq exit` / `b top`: the loop is an SDK `static inline` helper with its own locals.** No reshaping of the loop inside the caller (`while`/`for`/`goto`/`break`, copy placement, pragmas) removes the copy. Moving it into a helper written `do { old = cur; wait(); cur = read(); } while (cur != old);` does (`__GXAbort`, `0x80192190`, via the later SDK's `__GXAbortWaitPECopyDone`).
- **Inlined `UpdatePriority` loop with `priority`/`enabled` in swapped saved registers (`OSSetThreadPriority`, `0x80180DEC`):** declare the loop cursor `OSThread* t;` at function scope *before* `int enabled;`, not inside the `if`. This game's version has no asserts and ends with `if (RunQueueHint != 0) SelectThread(0)` instead of `__OSReschedule`.
- **Saved registers (r28-r31) rotated among plain locals with identical code:** MWCC hands them out in declaration order, first-declared local getting the highest register. Reorder the declarations (three locals = six permutations) before reshaping the code. `__CARDIsWritable` (`0x8040DE44`) needs `result`, `diskID`, `perm` in that order for r30/r29/r28; `__CARDIsReadable` (`0x8040DF78`) needs `perm`, `result`, `diskID` (assign after the declarations) for r30/r29/r28. If *no* declaration order moves it and a mid-function local outranks the parameters, the original called an SDK wrapper that MWCC inlined with its own `result` local: `CARDFastOpen` (`0x8040E1BC`) needed the later SDK's `__CARDIsReadable` as a `static inline` (`s32 result = __CARDIsWritable(card, ent); if (result == -10 && (ent->permission & 4)) return 0; return result;`), not the same test written in the caller.
- **Scratch registers (r4/r5) swapped in a function prelude with the frame 8 bytes short, every instruction otherwise identical (`ReadFont`, `0x8040310C`): the SDK source had never-assigned locals, and only the *declaration order of all locals, padding ones included*, fixes the allocation.** Add two unused `int`/pointer locals for the frame, then script a shuffle of the whole declaration list (about 60 random orders, several hit 100%); reordering the statements did nothing. The same function: a `for (y = 4; y < 8; y++)` loop using `(row + y)` inside the address expression (fully unrolled by MWCC) matched where `y = row + 4 + i` (or one big expression) stayed at 71-84%.

Using `RunQueue.x` directly makes the base rematerialisable: the loop cursor reuses its register and `lis`/`addi` is re-emitted before `OSClearContext(&idleContext)`. With the `rq` local (any declaration order) it matches. The later `queueMutex`/`stackBase`/`stackEnd` stores need `rq->defaultThread.x`, not `thread->x`; the queue-join init, `queueMutex.head = queueMutex.tail = 0` (inlined `OSInitThreadQueue`) and the active-queue enqueue are hand-written. This game's version calls `SwitchThreadCallback(__gCurrentThread, thread)` before `__gCurrentThread = thread` and `OSClearStack(0)` after it, and the `0x800000D8` (`__gUnkThread1`), `0x800000DC` (`__OSActiveThreadQueue`) and `0x800000E4` globals are declare-at-address. The original TU is `OSThread.c` (this function, `OSInitThreadQueue`, `OSGetCurrentThread`, `OSIsThreadTerminated`, scheduler helpers), but the `.sbss` (`RunQueueBits`/`RunQueueHint`/`Reschedule`) is claimed by the later `OSThread.c` unit, so a plain extern works.
- **Bus-clock tick math (`OSMicrosecondsToTicks`/`OSMillisecondsToTicks`/`OSNanosecondsToTicks`): declare the SDK's `u32 __OSBusClock : 0x800000F8;` (declare-at-address, as in `os.h`) and write the SDK macro inline where the SDK has it.** MWCC hoists a declare-at-address load out of a loop that calls a function, but it leaves `*(u32*)0x800000F8` in the loop, and the hoisted temps get different registers from a hand-written `u32 ticks` local. Applied in `DVDLowReset` (`while ((__OSGetSystemTime() - resetStart) < OSMicrosecondsToTicks(12))`), `DVDLowRead` (`OSMillisecondsToTicks(5)` written twice, no local) and `__OSResetSWInterruptHandler` (`OSMicrosecondsToTicks(100)` in the loop condition). If a unit still reads the bus clock through a cast, switch it first.
- **GX `GET_REG_FIELD` needs the SDK's `(int)` cast: `((int)((reg) >> (shift)) & ((1 << (size)) - 1))`** (ac-decomp `gx/__gx.h`). Without it, `__GXSetVCD` (`0x8018C3FC`) puts the `vcdHi` `clrlwi` into r0 instead of in place. A `(u32)` cast also matches there, but not in `__SetSURegs` (`0x8018E80C`), where it emits a second `add` for `gx + tcoord*4` instead of sharing one between `suTs0`/`suTs1`. ac-decomp's plain source, with `(int)` plus `* const __GXData` and direct `gx->` access, matches. Several units still use the uncast macro (`__GXCalculateVLim.c`, `GXGetVtxAttrFmt.c`).
- **An inlined setter called with a constant 0 that the original compiles to `ori r0,r0,0` (a `nop`): write the setter in plain C, not with `__rlwimi`.** After inlining, MWCC folds the insert of a constant zero into `| 0` and still emits the `ori`; `__rlwimi` keeps a real `rlwimi` from a zero register. `AIInit` uses ac-decomp's `SET_REG_FIELD` as a single statement, `__AIRegs[1] = ((u32)__AIRegs[1] & ~(0xFF << shift)) | ((u32)vol << shift)`, in `static inline` `AISetStreamVolLeft`/`Right` (a read/modify/write through a `u32 reg` local doesn't match). The standalone `AISetStreamVolLeft` still needs the `__rlwimi` form (see above), so the right form depends on whether the argument is a constant. The five `OSTime` bounds in `.sbss` (`lbl_8066F420`-`0x8066F440`) must be merged into `size:0x8` symbols.
- **`.sbss` globals defined in a unit come out in reverse declaration order, and a `(void)` pin makes no difference** (unlike the pooled `.bss` rule below). `DVDLowReset.c` declares `volatile u32 ResetOccurred;` before `volatile OSTime LastResetEnd;` to get `LastResetEnd` at `0x8066F340` and `ResetOccurred` at `0x8066F348`. They must be globals because `__DVDInterruptHandler` reads both.

  **Giving each an explicit `= 0` initializer instead flips this to forward declaration order**, and also moves the whole group ahead of any plain (no-initializer) `static`s the unit defines, rather than after them: MWCC's default plain `extern`-linkage uninitialized global is a tentative/common-style definition that the object file buckets separately (and in reverse) from ordinary `.sbss`, while an explicit-zero one is an ordinary definition laid out like a `static`, just non-`static` in scope. Use this when a unit's globals need forward order relative to each other or need to sit *before* the unit's own file-scope statics. Two pointer globals plus two `static` counters (`g_baseARAMtoVM`/`g_baseVMtoARAM = 0;`, then plain `static` `g_totalAllocatedVM`/`g_nextARAMPageToCheck`, `.sbss` `0x8066F970`, `VMAlloc.c`): without the `= 0`, the pair swapped order *and* landed after the statics; with it, they matched the original's forward order ahead of the statics.
- **GX `.bss` belongs to `GXInit.c`: define `FifoObj` and the `__GXData` block there, and write `&FifoObj` directly.** The SDK has `static GXFifoObj FifoObj; static GXData gxData;` in that file. With both defined (`GXFifoObj FifoObj; u8 lbl_8057D630[0x5B0];`, `.bss 0x8057D5B0-0x8057DBE0`), `GXInit` materializes `&FifoObj` straight into r31, as the original does. With an `extern`, it needs a `fifoObj` local and still routes the address through r0 plus an `mr`. The unit's `.sdata2` pool also needs `#pragma force_active on` (below).
- **One independent instruction scheduled a slot early or late just before an inlined call, everything else exact: load the call's first argument into a local on the line before.** MWCC evaluates an inlined call's arguments right to left, so `f(a->x, b->x)` puts the `b->x` load first in the pre-RA order, which moves unrelated instructions around it. `s8 stick = status->stickX; status->stickX = ClampS8(stick, origin->stickX);` put the original's `lis r5,Origin@ha` back after the preceding `stw` (`SPEC2_MakeStatus`, `0x8018AFC8`; only the four `ClampS8` calls take the local, giving the `ClampU8` calls one too breaks them). Check the order with `#pragma scheduling off` in a scratch TU.
- **A field-extract store with its address temp scheduled before it (`rlwinm`/`addi r28,r30,0x118`/`stw r0,0x118(r30)`) and a neighbouring `cmplwi` pulled one slot early, where the original has `extrwi` / `cmplwi` / `stw` / `addi r28`: write the extract as mask-then-shift, `(x & 0x300) >> 8`, not `(x >> 8) & 3`.** Both emit the same `extrwi`; only the scheduling changes. One of two adjacent extracts in that form is enough (`VIInit`, `0x801880D8`, `HorVer.nonInter`/`HorVer.tv` from `dspCfg`).
- **A boolean `x != 0` where the original is `neg r0,r3` / `or r0,r0,r3` / `srwi r3,r0,31` and ours is `subic`/`subfe`:** every `!= 0`, `!!x`, `? 1 : 0`, signed/bitfield form gives the `subfe` idiom. Write the original's arithmetic on an `unsigned long` local: `return (-v | v) >> 31;` (`__VMDoesMappingExist`, `0x80401140`).
- **A `switch` whose non-zero cases all share the default body compiles to `cmpwi`/`beq`/`b` where the original has `cmpwi`/`beq`/`blt`/`b`: list the SDK's case labels explicitly (`case 1: ... case 5: default:`).** The empty-looking labels still shape the compare chain (`OSGetFontEncode`, `0x804030A8`, `switch (*(int*)0x800000CC)`). A `peephole off` there gave a separate `cmpwi` and lost the `bnelr`/`rlwinm.` forms, so start with peephole on in a unit that has no earlier asm function.
- **A fixed-size block copy the original does as `lwz r0,N(src)` / `stw r0,N(dst)` word by word, where `*dst = *src` on a struct gives paired `lwz r4`/`lwz r0`/`stw`/`stw`:** cast both pointers to `unsigned long*` and write the copy as explicit `dst[i] = s[i];` statements (`AXSetVoiceAdpcm`, `0x8040943C`, 10 words). Take the destination pointer before the `OSDisableInterrupts` call, as the original does.
- **A loop-invariant 64-bit tick bound with the saved registers rotated (timeout hi/lo, start hi/lo one slot off) and identical code: write the macro inline in the loop condition, not into an `s64 timeout` local.** `while (!CallResetFunctions(0) ...)`-style `(OSGetTime() - start) < OSMillisecondsToTicks(1000)` matches; no declaration order of the three locals fixes the named form. A pointer local `OSBootInfo* bootInfo = (OSBootInfo*)0x80000000;` gives the hoisted `lis r30,0x8000` for the `0x38(r30)` read, and an `s32` return type on `VIGetRetraceCount` gives `cmpwi` for `(now - start) < 1` (`OSFatal`, `0x80402608`).
- **C++ class layout must be exact:** One wrong member offset breaks matching in that class, and vtable order must match the original virtual declaration order.

### Newlib / libgcc / tiny runtime functions are GCC output: write them as `nofralloc` asm

Scope: everything in `Runtime.PPCEABI.H` that comes from Newlib or libgcc (string, stdio glue, scanf/printf, libm floats, `atoi`, `__pure_virtual`), plus the small runtime wrappers around them. These were compiled by GCC, not MWCC, and MWCC C never reaches them. **Go straight to `nofralloc` asm; don't spend iterations on C.** Queue names for this range come from size and order only, so verify them.

Also scope: the whole `vm` library (`VM`/`VMBASE`, ARAM virtual memory, 0x804009C4-0x80401EB0) is GCC output too, unlike the rest of the Dolphin SDK. Every non-leaf function matched there so far needed `nofralloc` asm; only frameless one-line leaf getters/setters (no `bl`, no stack frame, e.g. `VMBASEIsPageLocked`, `VMBASEGetVirtualAddrFromPageInMRAM`) happened to compile identically as plain C, since a trivial leaf body is compiler-agnostic. A `vm` function with a stack frame or a `bl` is presumed GCC: check the **Tells** below (`VMBASEIsPageValid`/`Referenced`/`Dirty`, `0x80401488`-`0x80401500`, each `stwu`/`mflr`/`stw`/`bl`/`rlwinm`/epilogue) before writing C.

**Tells** (any one is enough):

| Tell | What MWCC does instead |
| --- | --- |
| `stwu r1,-N` first, then `mflr r0`, then `stw r0,N+4(r1)` (LR saved *after* the frame is made), incl. the `-8` frame of tiny wrappers | `mflr` / `stw r0,4(r1)` before `stwu`; a `-8` frame is never emitted |
| `mr. r3,r3` after a call; `addic.` / `subic.` loop counters; `stmw rN` *before* `stw r0` | `cmpwi`; `cmplwi`; the reverse order |
| Word-at-a-time null test: `andi. r0,rX,3` / `lwz` / `subis -0x101` / `subi -0x101` / `andc` / `and.`, with `lis`+`ori 0x8080` emitted twice; `cmplwi r5,3` / `ble` for `TOO_SMALL_LITTLE_BLOCK` | `clrlwi.`, one `lis 0x8081` constant, no peeled first-word check |
| Varargs prologue that saves only the *unnamed* args (`stw r5..r10`, r3/r4 never stored), `lis rX,0x200` va_list header, `bne cr1` skipping `stfd f1..f8` | `__builtin_va_info` saves r3-r10 with `mflr` first, on every compiler version; the va_list is also copied to a temp before the call (pass-by-value struct) |
| Unprototyped indirect call as `mtlr rN` / `crclr 6` / `blrl` | `mtctr` / `bctrl` |
| Temps allocated high to low (r9-r11 first), args never copied, shared `subi r3,r4,1; blr` exit, `stbu` in loops | r5-r7 plus copies, `stbx`, per-path epilogues |
| Float code via stack `stfs`/`lwz` (`GET_FLOAT_WORD`), `lis`+`ori`+`cmpw` constants, `clrlslwi` | (libm `tanf`) |

**Asm mechanics:**

- Frameless functions (`strncpy`, string routines) use only r0/r3-r5/r8-r11 and save nothing, so the asm has no prologue.
- Reference `.sdata` floats by bare name in MWCC inline asm (`lfs f2, lbl_8066C17C`); `@sda21(r0)` is a syntax error.
- Reference unclaimed `.data` as `extern char lbl_804D02A8[]` and use `@ha`/`@l` (like `isdigit`'s `lbl_8049C6A1`).
- A function that has its own symbol in `symbols.txt` needs its own `asm` function, even when it directly follows a no-return call (`terminate` after `fn_8017A5CC`'s `bl fn_8017A608`). Written as an `entry` label inside the preceding function, the bytes and `main.dol` still match, but objdiff sees one `0x3C` symbol against two targets and reports both at 0%. Keep `entry` for labels without their own function symbol, such as `__OSDBINTEND`.
- **`entry <label>` in `asm` needs the label declared first (`void _savegpr_14(void);`), else `undefined identifier`, and wibo then shows only "User break, cancelled" under ninja.** Rerun the mwcc command by hand to see the error. Multi-entry save/restore tables (`__save_gpr`, `__restore_gpr`, `0x80401EB0`/`0x80401EFC`) are one `asm` function with an `entry` per register, `r11` as base.
- **`crclr cr1eq` fails to assemble** (`illegal forward label ... (cr1eq)`): write the bit number, `crclr 4*cr1+eq` (or `crclr 6`), before a varargs `bl sprintf` (`asctime_r`, `0x80172CEC`).
- **MWCC asm SPR and paired-single operands:** `mfspr r3, HID2` assembles silently as the wrong SPR (`IABR`; objdiff shows `DIFF_ARG_MISMATCH`), so write the number (`mfspr r3, 920`). `psq_l f0, 0(r3), 0, qr0` fails (`undefined symbol (qr0)`); write the GQR index, `psq_l f0, 0x0(r3), 0, 0` (`fn_80003334`, `0x80003334`).
- **Data words a `.init`/asm function reads sit in the same unit as raw asm "functions":** claim the data with the function, and write the data as an `asm` function of `opword 0` (with `entry lbl_X` where the original has a second symbol inside it) with a `type:function size:N` symbol in `symbols.txt` (change dtk's `type:label data:double` entry). The function then references them by name with `lis`/`ori @h`/`@l` and the relocs match (`fn_80003334`).
- Calls to real functions are plain `bl name`, and the callee needs a prototype in the unit (`extern double __kernel_sin(double, double, int);`) or MWCC stops at `undefined label '<name>'`, which ninja shows only as "User break, cancelled". Other units' callers reference renamed functions by name in their own asm, so a rename means grepping `src/` for the old `fn_` name.
- `char` is signed on this target (`extsb`), so Newlib's `u_char` is `char`.
- **Two mnemonics the disassembler prints that MWCC's assembler rejects or misreads:** `cror un, eq, lt` (write the CR bit numbers, `cror 3, 2, 0`) and `subis rD, rA, 0x3f80` (write `addis rD, rA, -0x3f80`). A whole function can be generated from dtk's `.s` with a script (strip the address comment, `.L_` -> `L_`, `sym@sda21(r0)` -> `sym`, `subi rX, r13, N` -> `la rX, sym` on a sized `[4]` extern) and matches first try (`__ieee754_powf`, `0x8016D284`). The same script works for a big MWCC function when C is out of reach (`VIConfigure`, `0x80188A50`): also map `sym+0x4@sda21(r0)` -> `sym+4`, and `li rX, sym@sda21` -> `la rX, sym` on a sized `char[5]` extern; `clrlslwi`, `rlwimi` and the `@ha`/`@l` pairs assemble as printed.

**Old Newlib signatures:** stdio glue has no `reent` argument; `fp->_data` (`0x5C`) is the reent passed on. `FILE` is 0x60 bytes: `_p` `0x0`, `_flags` `0xC` (`lha`/`lhz`), `_file` `0xE`, `_bf._base` `0x10`, `_bf._size` `0x14`, `_seek` `0x28`, `_nbuf` `0x4A`, `_blksize` `0x54`, `_offset` `0x58`, `_data` `0x5C`. `__sglue` is at `reent+0x1D8` (`_next` 0, `_niobs` 4, `_iobs` 8). `_strtoul_r`/`_strtol_r` take `reent` first, and `_ctype_ + 1` is `lbl_8049C6A1` (flag bits `8` space, `4` digit, `3` alpha, `1` upper), used for any inlined `isspace`/`isdigit`/`isalpha`.

**Per function** (only what isn't derivable from the asm in `src/`):

- `strlen` (`0x80172780`), `strcat`, `strrchr`, `strcmp`, `strcpy` and `strncpy` are the non-size-optimised Newlib bodies (aligned word loop with `DETECT_NULL`, byte loop). Queue names here are by size only: `0x801727EC` (0x6C) is `strlwr` (lowercase-in-place loop calling `tolower`), not `strlen`.
- `strlwr`, `strnicmp` and `stricmp` are asm because of the GC/1.3.2 frame: the original is `-0x18` with `stmw r29,0xc(r1)` after `stw r0`; C gets the loop layout but a `-0x20` frame with `stmw` before `stw r0`. `optimize_for_size`, `scheduling off`, `register`, local order and `while`/`break` shapes change nothing.
- `__sccl` (`0x80170FB4`, scanf `%[` table builder): C with `optimize_for_size` gets the descending `bdnz` fill loop but none of the register allocation. `register`, `if` vs `switch` and every `opt_*` pragma do nothing.
- `_fwalk` (`0x80178A90`): signature `_fwalk(reent, func)` with `func(fp)`. Callers `__srefill`/`fflush`/`fn_80178684` reference it by name.
- `__smakebuf` (`0x80178B10`): always ends unbuffered (no malloc). Keep the `li r0,0; ori r0,r0,0x8000` pair for the `S_IFREG` compare verbatim.
- `atof` (`0x801711F0`, `strtod(s, 0)`), `atoi` (`0x80171214`, `strtol(s, 0, 10)`), `fn_8017A6CC`/`fn_8017A6EC`: bare wrappers with argument `li`s between the `stw` and the `bl`. `fn_8017A75C` looks varargs but never uses the va_list.
- `__pure_virtual` (`0x80179C30`): calls `terminate` (`0x8017A5DC`).
- `__ieee754_atan2f` (`0x8016D064`): Newlib `ef_atan2.c` (the `atan2f` errno wrapper is absent, callers hit this directly). The `switch` blocks compile to compare chains with duplicated tail blocks, so copy them literally. Its `.sdata` literals (`0x8066C0A0-CC`) are unclaimed `lbl_` floats referenced by bare name.
- `__ieee754_rem_pio2f` (`0x8016E8E4`): straight transliteration of Newlib `ef_rem_pio2.c` output. Its tables are `.sdata2` objects (`two_over_pi` `0x8066FE44`, `npio2_hw` `0x8067015C`), which the original reaches as `subi rX,r13,N`. Use `la rX, sym` with the extern declared **`extern const char sym[4];`**: with the real size (`[0x84]`) the compiler treats it as far data and emits `li rX,0 [R_PPC_ADDR16]`, while a small `const` size gives the sda21 reloc that bakes to the `r13` form.

## Data, symbols, and relocations

- **Fresh anonymous data doesn't reliably land at the original's address:**

  A plain-C `static` local or a fresh string literal can report 100% fuzzy, but the linker places it wherever, so the address computation bakes in the wrong small-data offset and `main.dol` breaks by a byte or two.

  The fix is to reference dtk's auto-detected symbol instead. dtk sometimes names these with a compiler-internal disambiguator such as `cmdTypeAndStatus$371`. `$` is not valid in this compiler, so rename it to a plain identifier in `symbols.txt` with `scope:global`, leave the range unclaimed in `splits.txt`, and use a plain `extern`.

- **dtk only preserves a hand-set symbol name if it doesn't look auto-generated:**

  Renaming a compiler literal (`@267 = .sdata2:0x8067078C`) to `lbl_8067078C` is silently reverted on the next build, because `lbl_*`/`fn_*` are dtk's own naming patterns and get regenerated. The rename also never reaches `build/GVLE69/sda_bake.json`, so your `extern` keeps an unbaked `R_PPC_EMB_SDA21` relocation where the original object has a plain `r13` offset. This is visible in `tools/objdiff_mismatches.py` as a `DIFF_REPLACE` on the `lfs`/`lwz`, not as a byte diff.

  Give it a real name instead (`GXInitZScaleConst`). That survives regeneration, lands in the bake list, and the relocation resolves.

- **Claiming a function can make dtk-dev rename symbols, and unclaimed callers then fail to link (`undefined: '<name>'`).** Keep the new name, set it `scope:global` in `symbols.txt`, and update the `extern`s in sibling units (including `lbl_`/`fn_` names inside their asm). Cases:
  - `.sbss` symbols the function touches (`lbl_8066F330` -> `StopAtNextInt`, `scope:local`; `DVDLowWaitCoverClose`): the next `ninja` rewrites `symbols.txt` and every other unit's `extern lbl_...` breaks.
  - A `.bss` static: dtk renames `lbl_XXXXXXXX` to `<Name>` (`scope:local`). Also add a `.bss start:.. end:..` line to the unit's split and define it non-`static` in the source (`__DVDClearWaitingQueue` / `WaitingQueue`).
  - A still-`fn_` function (`OSWakeupThread`, `0x80180CE8`): update the `extern`s in already-matched units too.
  - Two SDK statics with the same name (`AlarmHandler` in `SIBios.c` and `dvd.c`): dtk-dev renames the second to `AlarmHandler_<addr>`. Rename it that way (`scope:global`) and define the function non-`static` under that name. Same for a static name that already exists as a global (`BootInfo` in `OS.c` and `dvdfs.c`, else mwld reports `multiply-defined`): give the later one by address the `_<addr>` suffix (`BootInfo_8066F2A0`).
  - **Which occurrence gets the suffix matters, not just that one does.** If the colliding name was already attached to an *unclaimed* address (dtk's own auto/signature-derived name, visible in `symbols.txt` before you touch anything), renaming *that* occurrence to `_<addr>` — even with `scope:global` and even though `main.dol`'s own symbol table ends up correct — leaves other, unrelated, already-`Matching` units' baked `R_PPC_EMB_SDA21` immediates pointing at your new symbol's address instead (a handful of 2-byte `.text` diffs scattered across distant functions, `main.dol` size unchanged, `readelf -s` on `main.elf` shows the right address for both symbols regardless). Give the suffix to *your newly introduced* symbol instead and leave the pre-existing name/address untouched, even if yours is the lower address (`ResetSwLastState` vs `LastState`, `0x8066F258` pooled into `__OSResetSWInterruptHandler.c`, colliding with dvd.c's already-auto-named `LastState` at `0x8066F314`).
  - A `static` function claimed while its caller is still unclaimed (`cb` in `fstload.c`, `0x80186A80`): rename it `cb_<addr>` and define it non-`static` under that name (self-references in the source too). `tools/objdiff_mismatches.py` needs the full unit path (`Dolphin/dvd/fstload`) and the function name as linked (`cb_80186A80`).
  - An SDK anchor with a signature (`OSInit`) renames far beyond its unit (about a dozen symbols project-wide, including the SDK's `@1`/`@116` literal names), can expose a mis-split (`Symbol ... overlaps with symbol ...`; `fn_8017E5E0` really starts at `0x8017E5CC` as `__OSInitMemoryProtection`), and teaches dtk the linker symbols (see the LCF note below). Update every sibling `extern`, and fix any `scope:local` a C unit references.
  - Naming `EXIInit` (`0x8019509C`) re-derived `Ecb`, `EXIImm`, `EXISync`, `EXIGetID`, `__OSEnableBarnacle`, `__OSInIPL`, `IDSerialPort1`, `memmove`, ... and flipped `Ecb`/`TCIntrruptHandler`/`IDSerialPort1` to `scope:local`. `sed` the old names across `src/` and flip the shared ones back to `scope:global`; `main.dol: OK` afterwards confirms nothing moved.

- **Prefer referencing an unclaimed symbol over claiming its range:**

  Claiming even a 4-byte `.sbss` range can repack every other unclaimed symbol in that section.

  The same applies to `.data` statics with cross-object callers: claiming a range to define `Si` as a true `static` broke the link (`undefined: 'Si_804D1BBC'`) from still-unclaimed functions. Override `scope:local` to `scope:global` in `symbols.txt` and use a plain `extern` instead. Hand-set attributes persist across regeneration.

- **Original loads `lwz rX, sym+0x8@sda21(r0)` (a scalar at an offset into a multi-word `.sbss` symbol): split the symbol in `symbols.txt` into one 4-byte entry per word and `extern` each as a scalar.** An array or struct extern covering the blob gives `li rX, sym@sda21` + `lwz 0x8(rX)` (or `lis`/`addi` when it is over the small-data threshold), and an over-sized array indexed past its end does not help. Other units' asm is regenerated against the new names (`VMBASEIsPageLocked`, `lbl_8066F97C` -> `lbl_8066F97C`/`80`/`84`/`88`).
- **`addi` does not accept the bare-symbol sda21 trick:** "Bare symbol name, no base register" only works for instructions with a real `d(rA)` operand such as `lwz` or `lfd`. For address computations, use `la rD, symbol` and give the symbol a sized declaration such as `extern char lbl_8066C408[8];` rather than `[]`; the size is what fixes the relocation type.

  Getting it wrong produces the wrong relocation, visible via `tools/objdiff_mismatches.py`, not a byte diff.
- **A `.sdata2` object you *define* in a unit must be split into definitions of at most 8 bytes each (the default `-sdata2 8`), or mwld fails outright with `Relocation (3) of symbol '<name>' in '<unit>.o' is out of range`:** MWCC puts a larger `const` object in far data, so `la rD, sym` gets `R_PPC_ADDR16` instead of the sda21 form. Define a 16-byte `Zero[2]` as two consecutive scalars (`const double A = 0.0; const double B = -0.0;`) with one `symbols.txt` entry each; asm that indexes the pair by a computed `+8` still reaches the second (`Fmod2ZeroConst`/`Fmod2NegZeroConst`, `0x80670858`, `__ieee754_fmod2.c`).
- **Even an *array* small enough to fit the `-sdata2 8` threshold (e.g. `const float Bp[2]`, 8 bytes) makes `la rD, sym` silently wrong when the array is defined in the same unit that indexes it: no relocation is emitted at all (not even the `R_PPC_ADDR16` above) and MWCC bakes some unrelated fixed `r13` displacement instead, giving a byte-identical `report.json`/objdiff but a wrong `main.dol`.** Only a real C *array* type triggers this; a run of same-sized scalar globals doesn't. Fix: never define a `.sdata2` array a unit's own code indexes — split it into one named scalar per element (`PowfBp0Const`/`PowfBp1Const`, …), take the address of element 0 with `la`, and index with the same runtime `lfsx`/`lwzx` offset the original uses (`KernelRemPio2fInitJk0`/`PIo2Const0`, `__kernel_rem_pio2f.c`; `PowfBp0Const`, `0x8066FC20`, `__ieee754_powf.c`). A *large* same-unit `.sdata2` array (well past the 8-byte threshold, e.g. a 66-element table) fails louder instead of silently: `la rD, sym` compiles to the far-data form and `mwldeppc` aborts with `Relocation (3) of symbol '<sym>' is out of range` at link time. This happens even when the unit's own code only takes the array's address and never indexes it itself (the index happens in a different, callee unit) — the same per-element-scalar split fixes it (`RemPio2TwoOverPi0`..`65`, `__ieee754_rem_pio2.c`, address only taken, passed on to `__kernel_rem_pio2`).

- **A same-unit `.sdata` array over the default `-sdata 8` threshold (e.g. a 12-byte `u32[3]`) is routed to `.data`-style `lis`/`addi @ha`/`@l` addressing instead of `@sda21`, even though `splits.txt`/`symbols.txt` say `.sdata`, and even when only element 0 is ever read.** dtk's auto-namer merges a trailing run of unreferenced zero words into the last real object's symbol (see the merged-blob rule above), so a 4-byte referenced scalar can show up in `symbols.txt` as a misleadingly large one (e.g. `size:0xC` for one real `0xFFFFFFFF` word plus 8 bytes of unreferenced padding). Defining the object at that inflated size breaks `main.dol`. Fix: shrink the definition to the array's real referenced size (`u32 lbl_8066C424[1] = { 0xFFFFFFFF };`, not `[3]`) and end the unit's `.sdata` split before the trailing padding, leaving those bytes unclaimed for dtk to keep auto-emitting (`lbl_8066C424`, `0x8066C424`, `dvd.c`). The `.sbss` equivalent shows up as a hard link failure instead of a silent diff, because other already-`Matching` units' `extern`s were compiled expecting `@sda21` addressing: `mwldeppc.exe Linker Error: Small data relocation (109) ... requires that symbol '<name>' ... be in a small data section but is in .bss`. Same fix, same inflated-dtk-size cause: shrink the object to its real size (`FinishQueue`, an 8-byte `OSThreadQueue`, not the dtk-merged `size:0xC` that included 4 bytes of alignment filler before the next symbol) and leave the remainder unclaimed (`GXDrawDone.c`, `0x8066F49C`).
- **An unreferenced (`force_active`'d) object over 8 bytes defined for a `.sdata` claim is placed in `.data` outright, not just given `.data`-style addressing: `main.dol` grows by its size (alignment padding) with no error.** `-sdata 8` gates *section placement* for an object nothing in the TU ever addresses, same as `-sdata2`/`-rodata` do for `const` data; the `.data`-addressing-only symptom above is for an object that *is* referenced. Fix: split it into several `<=8`-byte globals (one per original C object: a string, a zero-filled array) instead of one bigger aggregate — each stays in `.sdata` on its own (`SIGetTypeStringBusy`/`Unknown`/`Pad`, `0x8066C3EC`, replacing a single 0x18 struct).
- **Before hardcoding an address as a raw immediate because the target "isn't split yet", rebuild once and grep `symbols.txt`:** dtk's auto-namer may already have named it. Hardcoded `lis`/`addi` immediates stall around 99% because the original carries real `R_PPC_ADDR16_HA`/`_LO` relocations; `symbol@ha`/`@l` matches.
- **The auto-namer may only tag part of a merged data blob:**
  For example, it may name the first 0x30 bytes of a 0x98-byte blob and leave the rest as a separate `lbl_`.
  It also merges a *trailing unreferenced* object into the preceding symbol (nothing relocates against it,
  so there is no boundary to find), which inflates any size scouted from dtk's symbols. Before claiming a
  data range, count the reference's constants and claim only those; split the merged symbol in
  `symbols.txt` and leave the orphan as its own `lbl_` for dtk to emit (`scalbn.c`'s four `s_scalbn.c`
  doubles at `0x8066C370`, scouted as five because a stray `0.0` at `0x8066C390` was merged into
  `lbl_8066C388`). Auto-names also often come back as `scope:local`, and they may need a manual override to `scope:global` before your object can reference them.
- **A byte-array literal copied verbatim from the reference source (a DSP microcode blob, a lookup table) with no nearby claimed symbol to anchor its address: byte-search `orig/GVLE69/sys/main.dol` for the exact bytes, convert the file offset to a virtual address via the DOL header's per-section offset/address/size triples, then `grep` `symbols.txt` at that address.** dtk's auto-namer often already merged it into a larger anonymous blob (see above); split out just the literal's real size and rename it, leaving the remainder (usually an unrelated neighbour's data) as its own entry. Confirms the address without guessing or waiting on a `main.dol` diff. Example: `CardData` (`__CARDUnlock`, `0x8040FD5C`), split out of `lbl_804F2C20` (0x19C total; the trailing 0x3C was `texPalette.c`'s unrelated version-mismatch strings).
- **Trailing alignment padding in a claimed `.data`/`.bss`/`.sbss` range keeps the unit's data below 100% in objdiff even when the code is 100%:** the original object was cut with the linker's padding to the next object still inside it, but MWCC's object is unpadded (`Scb` 0x58 vs 0x54, `Reschedule` 8 vs 4). Code stays `Matching` and `main.dol` is unaffected, but objdiff scores the section as a mismatch and drops its bytes from "SDK Code Data". Fix: shrink the last symbol in `symbols.txt` to the object's real size. objdiff diffs a data section only up to the end of its last symbol and ignores dtk's hidden `gap_` padding symbols, so the split end can stay 4-aligned (dtk requires that, `Invalid alignment for split`). With 4 bytes or more of padding you can also end the split at the object's end (`Scb` 0x54, `Reschedule` 4). If the next symbol lies beyond the split end, the `gap_` symbol overruns the split and `REPORT` fails with `size out of section bounds`; end the split where the next unit's range starts instead (`__OSBootDolSimple` `lbl_804D1218` 0xB, split end `0x804D1228`; `__OSCacheInit`, `OSResetSystem`).

  **This only works to *shrink* a range your compiled object already reaches; it doesn't widen one.** Extending an already-`Matching` unit's split end past a still-unclaimed `lbl_` symbol, without defining any new object for those bytes, does not make dtk backfill the gap from the original dol — the linker still emits your object at its real (unchanged) size, so whatever follows (the next real or auto-generated object) shifts earlier by the gap's size and `main.dol` breaks with thousands of diffs from that point on. A real, unreferenced-but-`force_active`'d object (as in the pooled-literal/dead-string rows elsewhere in this file) is what's needed instead, sized to actually produce those bytes (`__AXSyncPBs.c`, `.data` `0x804EF0A4`, 0x1C bytes of alignment padding before `__AXCompressorTable`).

  **The reverse mistake is claiming *more* than you need to.** When a `.bss`/`.sbss` symbol dtk reports is oversized because it merged a real, referenced word with trailing unreferenced alignment filler before the next already-claimed unit, don't extend the split to that full size and try to invent an object for the filler — just claim and define the real word alone (ending the split there) and leave the filler unclaimed for dtk to keep emitting, exactly as if it were still part of an untouched blob. This is safe specifically because `.bss`/`.sbss` content is always zero regardless of who "owns" it on paper, so there is nothing to get byte-wrong. Example: `VMLRUCursor` (`.sbss` `0x8066F968`), where dtk's `lbl_8066F968` was sized 8 (the real 4-byte cursor plus 4 bytes of padding before `VMAlloc.c`'s 8-aligned data); claiming only the first 4 bytes reached 100% with no padding trickery needed.
- **Claiming a 32-aligned object whose size isn't a multiple of 32 moves the *next* unit's `.bss` down if that unit doesn't declare its own alignment:** `main.dol` fails with ~200 scattered byte diffs, and the next symbol lands 8-aligned right after the claimed object's real end (`__AXPB` at `0x806570F8` instead of `0x80657100`). Give the next unit's definitions the SDK's `__attribute__((aligned(32)))` (`ATTRIBUTE_ALIGN(32)`). Only the object at the section's start is load-bearing, since MWCC takes a section's alignment from the max over its objects; keep it on the rest anyway where the SDK would have it (anything `DCFlushRange`d). Do **not** instead pad the claimed object to the gap or round its `size:` up, which fakes padding the linker derives and costs the unit's objdiff data score (see the trailing-padding rule above). Example: `__AXSyncPBs.c`'s `__AXPB`/`__AXITD`/`__AXUpdates`, after `__AXPrintStudio.c` claimed the 0x36-byte `__AXStudio`. The same shift appears while that unit is `NonMatching` (for example after merging more functions into it): dtk writes the extracted original object's `.bss` with 8-byte alignment. Add `align:32` to the unit's `.bss` line in `splits.txt`.
- **A switch's jump table is a lone anonymous `.data` object, and MWCC always gives that section 8-byte alignment:** a unit whose claimed `.data` starts 4-mod-8 therefore lands 4 bytes late, and `main.dol` breaks with thousands of scattered diffs (everything after shifts) even though the function's own fuzzy match reports 100%.

  **The fix is to widen the unit until its `.data` is 8-aligned**, i.e. reconstruct the original translation unit. Table addresses mark the object boundaries: tables packed with no gap are one object, a 4-byte gap is the padding before the next. Claim every function from the first table's owner onward and keep the unit's `.text` contiguous, since an object contributes one contiguous `.text` block and functions sitting in between have to come along (`GXSetVtxAttrFmtv`, `GXSetTexCoordGen2`, `GXInitTexObj`). Where the rest of the original file is still asm, see the pool trick below (`VIGetTvFormat`).

  **Only the *start* of the claimed range has to be 8-aligned.** A range that *ends* 4-mod-8 is fine, because what follows is one of dtk's own asm objects, which carries the original's 4-byte alignment rather than MWCC's 8. So a function whose own tables start 8-aligned can be split on its own even when the rest of its translation unit isn't ready (`GXSetGPMetric`, `.data 0x804D3738-0x804D3824`). The reverse fails: `GXReadGPMetric`'s own table starts at `0x804D3824`, so it had to join `GXSetGPMetric.c` (`.text 0x8019342C-0x80193E1C`, `.data 0x804D3738-0x804D3880`).

  **A merged-in function with no callers gets dead-stripped once the unit is `Matching`:** the link drops it with its jump table, and `main.dol` comes out shorter (`GXReadGPMetric`, 480 bytes). Add the function to `force_active` in `config/GVLE69/config.yml`.

- **The same 8-byte-start rule applies to any `.sdata`/`.sbss` claim, not just a `.data` jump table, and an `asm` function's data has no neighbour to widen into.** Claiming a small-data block that starts 4-mod-8 -- a lone float, or a whole run of constants -- still gets its object's section pushed to the next 8-aligned address, landing 4 bytes late with the same thousands-of-diffs symptom (`main.dol` grows +32 even while the unit reports 100% data). Fix it the same way: widen the claim to include the adjacent already-open data row that ends (or starts) exactly on the misaligned boundary, so the combined object is 8-aligned at both ends, and have the *other* row's unit `extern` what it needs instead of defining it (same "later owns, earlier externs" shape as the `.sdata2` pool-sharing bullet below). Example: `cosf.c`'s lone zero float at `0x8066C174` (4-mod-8) only works once its claim is widened back to `0x8066C160` to absorb `atanf.c`'s 5 preceding floats (8-aligned start, 0x18 total); `atanf.c` externs them by name. `tanf.c`/`sinf.c`'s zero floats at `0x8066C178`/`0x17C` pair up the same way. Whole blocks pair the same way: `__kernel_sinf.c`'s 7 `kf_sin.c` floats at `0x8066C28C` widen back to `0x8066C268` to absorb `__kernel_cosf.c`'s 9 (0x40 total, 8-aligned both ends), which then externs them.
- **Plain `.bss` needs the same 8-byte start too (dtk-dev warns `Alignment for <unit> .bss expected 8, but starts at <addr>`), and two separate arrays declared side by side in the widened unit do not land in address order: MWCC lays out same-sized-class unreferenced globals by its own heuristic, not by declaration order, so swapping the source order of the two arrays has no effect.** Declaring them separately can silently swap which one sits at the lower address, breaking every `@ha`/`@l` reference to both. The reliable fix is to merge the two into *one* array sized to the combined range under the lower (absorbed) symbol's name, and reach the higher one by offset arithmetic on that symbol -- `(Symbol+0xNN)@ha` / `(Symbol+0xNN)@l` (parens required; `Symbol@l+0xNN` is a syntax error) -- exactly like the `.rodata.1` two-const case below, dropping the second symbol's own `symbols.txt` entry entirely. Example: `_vfwrite.c`'s own 0x80-byte buffer at `0x8057C024` (4-mod-8) had to widen back to `fftoa.c`'s preceding 0xA4-byte buffer at `0x8057BF80` (8-aligned); one `lbl_8057BF80[0x124]` array replaces both symbols, with `_vfwrite`'s buffer reached as `(lbl_8057BF80+0xA4)@ha`/`@l` and `fftoa.c` keeping its plain `extern char lbl_8057BF80[];`.
- **An explicit-zero scalar global (`float x = 0.0f;`) is folded into `.sbss` by MWCC even with `-common off`, landing at the wrong address for data the original placed in `.sdata`; only *non-zero* scalar globals stay in `.sdata`.** This is independent of the 8-byte start-alignment issue above and needs its own fix: wrap the zero value so it no longer looks like a plain zero-initialized scalar, e.g. `struct { float v; } X = {0.0f};` (accessed as `X.v`), which keeps it in `.sdata`. A `float x[1] = {0.0f};` array also avoids the `.sbss` fold, but arrays get their own object 8-aligned regardless of an `__attribute__((aligned(4)))` override, so prefer the struct form when the symbol must sit at a non-8-aligned address (`CosfZeroConst`, `0x8066C174`). Negative zero (`-0.0f`, `0x80000000`) is not folded and needs no wrapper (`Atan2fNegZeroConst`, `0x8066C0C4`).
- **A data row that claims a `.sdata` scalar and calls it "+ N pad" or otherwise implies it's zero: check the original DOL's actual bytes at that address before defining it as `Type x;` or `x = 0`.** dtk placing something in `.sdata` rather than `.sbss` is itself a hint it was non-zero-initialized in the source (a tentative/zero definition is `.sbss`'s natural home); declaring it as zero/uninitialized makes MWCC route it there instead, same symptom as the explicit-zero fold above (thousands of one-byte `text` diffs from every later `r13` displacement shifting, `main.dol` size unchanged). Read the real value straight from `orig/GVLE69/sys/main.dol` at the symbol's file offset rather than guessing. `FirstRead` (`dvdlow.c`, `.sdata` `0x8066C480`) is `s32 FirstRead = 1;`, not `0`.
- **A non-zero 4-byte scalar global that belongs in `.data` is put in `.sdata` by MWCC (`-sdata 8` is the default in `cflags_base`), so the claimed `.data` object is simply absent: everything after it in `.data` slides up by its size, `.sdata` grows, and `main.dol` breaks with tens of thousands of diffs.** Pin it with `__declspec(section ".data")`; unlike `.rodata.1`, `.data` is predefined so no `#pragma section` is needed (`lbl_804D0678`, `fn_8017A620.c`). The same holds for a small *uninitialized* global that belongs in `.bss`: it lands in `.sbss`, `.sbss` grows and every `r13` displacement in the DOL shifts (thousands of one-byte `text` diffs plus the bss-size byte at header `0xDF`). Pin it with `__declspec(section ".data")` too -- MWCC rejects `".bss"` with `only use the initialized section name to refer to the section`, and routes an uninitialized object declared in `.data` to `.bss` (`initialized`, `0x8057C4F0`, `__main.c`).
- **A `const`-qualified array/global you define for a `.data` claim is routed to `.rodata` instead, even though `symbols.txt`/`splits.txt` say `.data`:** MWCC sends `const` objects above the small-data threshold to `.rodata` purely from the qualifier, regardless of the claimed output section (`.rodata.1` needs its own `#pragma section`/`__declspec`, but plain `.rodata` is the silent default for any large `const`). The symptom is `.rodata` growing by the object's size with everything after it in that section shifted, while the unit's own objdiff/report score still reads 100% data (the bytes match, just in the wrong section) — only `main.dol` catches it, with thousands of diffs starting at the old `.rodata`/`.rodata.1` boundary. Fix: drop `const` so it stays a plain non-`const` global (`powersOf10`, `0x804D02D0`, `strtod.c`); the SDK's own object being writable-section is why the original placed it in `.data` to begin with.
- **A `Matching` unit that owns a `.sdata2` range needs `#pragma force_active on`:** `dtk elf bake-sda` turns every `.sdata2` access into a fixed `r13` offset and deletes the relocation, leaving MWCC's anonymous literal pool (`@39`, `@40`, ...) unreferenced for mwld to dead-strip. The symptom is `main.dol` short by exactly the unit's `.sdata2` size, that section repacked from its first byte. (dtk's own objects survive because *unclaimed* data is emitted by dtk, not mwld; a named, non-`static` `const` global you define yourself is stripped just the same once its only readers are inside the unit, `asm` bodies included — `FmodfZeroConst`, `0x80670880`.) The pragma also keeps any otherwise-uncalled function in the unit (`GXSetFog`, `__GXGetTexTileShift`). If the unit also has a `static` helper the original inlines everywhere, put the pragma *after* the helper's definition: at the top of the file it keeps the helper's out-of-line body too, and `main.dol` grows by its size (`GXGetYScaleFactor` merged with `GXSetDispCopyYScale`, `__GXGetNumXfbLines` +0x60). If the literals belong to the helper's own body, placing the pragma after it isn't enough: MWCC creates the pool while compiling the helper's out-of-line copy, before the pragma, and `main.dol` comes out short by the pool size. Declare the helper `static inline` so it is only ever compiled inlined (`Halt`, `0x804027E0`, with `RGB2YUV`). **The pragma can also become newly required on a unit that already matched standalone**, once a *second*, sibling `Matching` unit starts `extern`-referencing its `.sdata2` data (see the next bullet): `main.dol` stays the same size but gets corrupted starting at that data's first byte (`C_MTXOrtho`, once `C_MTXPerspective` externed its constants).
- **An unreferenced literal inside a claimed `.sdata2` range must be a non-`static` named `const`; `#pragma force_active on` does not rescue a `static` one.** When a per-function unit claims part of the original translation unit's shared pool, the claim can include a constant only the *other* functions of that TU use. A `static const f32 x = 1.0f;` nothing in the unit reads is dropped by the compiler before force_active can matter, and the slot links as zeroes: `main.dol` keeps its size and `diff_dol.py` reports exactly those bytes differing. Define it as a plain global `const f32 Name = ...;` with a real (non-`lbl_`) name, placed after the function whose anonymous literals precede it so the pool order holds, and give the same name to its `symbols.txt` entry (`GXProjectWConst`, `0x80670774`, `GXTransform.c`).
- **Two functions from one original source file (e.g. `mtx44.c`'s `C_MTXPerspective`/`C_MTXOrtho`) sharing a float literal pool, where the earlier-in-`.text` function needs constants that live *after* the later function's own pool:** splitting each function's `.sdata2` by address creates a cyclic link-order dependency (`.text` wants A-before-B, `.sdata2` wants B-before-A) that dtk's `dol split` rejects outright. MWCC's literal-pool order for a merged translation unit does not follow source/`.text` order (confirmed empirically here: swapping source order to fix the pool broke `.text` placement instead, and named `static const` locals pooled identically to bare literals either way) — merging into one compiled TU is not a usable fix either, since pool order stayed tied to whichever function's code the compiler happened to place first. The working fix: keep them as **separate units**; the later (`.text`-wise) function owns the *entire* contiguous constant block including the earlier function's exclusive values (extend its `splits.txt` `.sdata2` end past its own needs); the earlier function `extern`s everything it needs from that block. Declare the externs `extern const float X;` — plain `extern float X;` (no `const`) defeats CSE, forcing a reload before every single use instead of one load reused across the function (a `DIFF_INSERT`/`ARG_MISMATCH` storm, not an address mismatch). Give the shared symbols real names in `symbols.txt` (`scope:global`), not `lbl_`/`fn_`-pattern ones — an auto-pattern name is silently reverted and the `extern` keeps an unbaked relocation (see the rename bullet below). Don't give the owning unit's *own* code a `const`-qualified named alias for its own literals to "share" the definition — the compiler treats a referenced `const` global as a proven-constant value and additionally constant-folds it into a *second*, separate anonymous literal for that function's own use, duplicating the data and shifting every address after it; plain bare literals in the owning function's own body, alongside the named `extern`-only constants nothing in that unit touches, avoid the duplication.
- **`bl lbl_XXXX` vs `bl __shr2u`/`__shl2i` (u64 shifts) is a symbol-name diff, not a code diff:** the runtime helpers are anonymous `type:label` entries in `symbols.txt` (`0x8016B59C` = `__shr2u`, `0x8016B5A4` = `__shl2i`, `0x8016B5AC` = `__shr2i`, the signed `s64 >>`). Rename them as `type:function size:0x4 scope:global` (like `__div2i`) so objdiff resolves the call. The same goes for an 8-byte `.sbss` u64 that dtk split into two 4-byte symbols (`lbl_8066F3B8`/`BC`): merge into one `size:0x8`, else the low-word access shows as `lbl+0x4` vs `lbl_..BC`.
- **Base of a `.bss` table hoisted to the prologue (`lis`/`addi r31`, used later with `0x78(rX)`/`0x144(r31)` displacements): take `u8* tbl = table;` as the first local, pass it to the inline helpers, and index as `((u16*)(tbl + 0x78))[i]`.** Without the local the `lis`/`addi` is emitted out of line at the tail. `*(u16*)(tbl + i * 2 + 0x78)` and `((u16*)tbl)[i + 0x3C]` leave a stray `addi`/`lhzx` (`__VIRetraceHandler`, `0x80187B3C`). A sized extern (`u8 q[8]`) gives the `li rX, sym@sda21` form for a queue address.
- **Two adjacent `.bss` arrays addressed as `add r5,r31,r0` / `addi r5,r5,0x1680` (constant added *after* the index add, and derived `+0x280`/`+0x500` taken from that result) are pooled objects defined in the unit; an `extern` array always folds the constant (`addi r3,r5,0x1900`, or `mulli`/`addi`/`add`).** No pointer local, 2D/3D array shape or `+ 3` row index changes that. Claim the `.bss` range, define both as non-`static` arrays (`unsigned char __AXBufferAuxA[3][0x780]; ... B[3][0x780]`) and index them directly. Other units keep `extern`s (rename `lbl_` to real names in `symbols.txt` and their sources). Test in a scratch TU with `static` arrays first (`__AXProcessAux`, `0x80406FE0`).
- **Lookup tables read as `add rX,rBase,rIdx` / `lwz rY,0x54(rX)` (offset in the displacement, base held in a saved register with no reloc) where ours is `addi rX,rIdx,0x54` / `lwzx`, and the original re-emits `addi r3,rBase,0x3d00` per use where ours CSEs it into a saved register: the tables and buffers are `static`/global objects defined in the unit's own pool.** An `extern` array or struct with a `tbl` local gives the `lwzx` form however the index is spelled. Claim the `.data` (start 8-aligned; it may end 4-mod-8) and `.bss` ranges, split dtk's blob per object in `symbols.txt`, and define the arrays with their initialisers in declaration order (`__AXSyncPBs`, `0x80408D44`: three `static unsigned long` cost tables, and `__AXPB`/`0x1000`/`0x4000` `.bss` buffers). Sum the table reads as one `cycles += b[..] + c[..] + c[..] + 0x8C;`; other groupings are reassociated differently (script a sweep of the shapes).
- **A pointer local that gets `add r3,..` / `lhz 0xe(r3)` / `addi r26,r3,0` where the original computes it straight into the saved register (`add r26,..` / `lhz 0xe(r26)`): assign it inside the first use, `if ((pb = &pbs[p->index])->state == 1)`.** A separate `pb = ...;` statement, a nested declaration with initialiser and every declaration order keep the copy (`__AXSyncPBs`). The same lever fixes a pooled `.bss` base (`lis`/`addi r3`) that ours materializes after the first block's arithmetic (so a temp like `srwi r3,r0,31` takes its register) where the original has it before: `if ((frames = *hostSum / 160) != 0)` instead of `frames = *hostSum / 160; if (frames)`. It only works with the object defined in the unit; with an `extern` the base is rematerialized per use (`__AXPrintStudio`, `0x80408134`). A countdown `for (pri = 31; pri != 0; pri--)` gives the original's `subic.`/`bne`; `pri > 0` gives `bgt`.
- **A prologue of zero stores to `.sbss` globals where ours has the zero constant and the pool-base `lis` temp in swapped scratch registers (zero in r3 after the mode store, base `lis r4` hoisted first; original `li r4,0` first, `lis r3` after the `stw r3`): declare the zero-stored globals `volatile` in that unit.** It pins their store order and lets the argument stay live across them; no statement reordering (all 24 store permutations) or local declaration order changes it. Only the zeroed globals, not the one that receives the parameter (`__AXOutInit`, `0x80407D30`, `volatile` on `lbl_8066FA60`/`64`/`84`, plus its two `.bss` buffers defined in the unit).
- **Identical instructions with only scratch registers rotated in a run of `x++` / `x %= 3` on independent globals (const `0xAAAAAAAB` in r8 instead of r0, values in r10/r9): sweep the interleaving of the increments and the mods.** Statement order changes pre-scheduling live ranges, so it moves allocation without changing the count. Keep each mod after its own increment and the store order fixed, then try all merges (about 120 builds, seconds with a scratch compile scored by opcode/register halfwords). The winner had a later increment between two mods (`__AXProcessAux`).
- **`lis`/`addi r31` to one `.bss` object, then `addi rX,r31,0x20` / `addi rX,r31,0` to reach the object *after* it, means pooled data, not a pointer local:** MWCC addresses objects defined in the same unit off one base (`...bss.0`), and the `+0` form stays an `addi`, never `mr`. No `extern`/local-pointer form reproduces it. Even an `extern` struct spanning the pool, with a base local, only gets the instructions: the frame came out 16 bytes short and the loop's pointer induction variables rotated until the arrays were defined in the unit (`__AXVPBInit`, `0x80409008`, reaching `__AXITD`/`__AXUpdates`/`__AXVPB` as `__AXPB+0x3D00`/`+0x4D00`/`+0x8D00`). If the object is already defined by a neighbouring function's unit, merge the functions into one unit rather than trying more C shapes (`CARDInit`, `0x8040B004`, merged with `__CARDGetFontEncode`/`__CARDSetDiskID` into `CARDInit.c`; the extern form stuck at 96% with `addi r3,r3,@l` + a later `addi r30,r3,0`). Claim the unit's `.bss` range and *define* the objects in the source. Keep them non-`static` so unclaimed asm still links (globals pool too). Layout rules: `static`s follow declaration order; globals go referenced-first in **first-use order**, then unreferenced ones in reverse declaration order. A discarded `(void)obj;` counts as a use and emits nothing, so it can pin the order. Place it where nothing else is live (at the end of `stateReadingFST` it stretched the pool base's lifetime). Example: `stateCheckID` (`0x80184688`, `dvd.c` `.bss 0x8057D220-0x8057D2B8`). With two pools (`.data` and `.bss`) in saved registers, the pool the unit touches first gets the higher register (r30 vs r29), so put the pins at the top of the unit's *first* function when the real TU used that pool first (`getTiming` in `VIInit.c`, standing in for `vi.c`'s `__VIRetraceHandler`).
- **Pooled `.bss` owned by another unit: declare it as one extern struct plus a local base pointer.** `__DVDInterruptHandler` addresses `CommandList`/`AlarmForTimeout`/`Prev`/`Curr` (defined in `DVDLowRead.c`) off one saved register (`lis`+`addi r30`, hoisted to the prologue). Separate externs give a `lis`/`addi` per symbol. Mirror the layout in a `DVDLowBss` struct, `extern DVDLowBss CommandList;` (the first symbol, so relocs stay `CommandList@ha/@l`), plus `DVDLowBss* bss = &CommandList;` as a local declared last: that gets the hoisted base and the extra `stmw r27`. Pass `bss` into the inlined `ProcessNextCommand` too, or it re-materializes the address. No need to merge the TUs. The `(void)` trick from `DVDLowRead` only fixes pool order for *defined* symbols.
- **A switch-only function whose jump table sits 4-mod-8 can still be its own unit if the *pool it addresses* is claimed from an 8-aligned start (`getTiming`, `0x80187E38`):** the function loads the pool base (`lis`/`addi lbl_804D2880`) and adds `0x44`-style offsets, and the table `0x804D2A74` follows the pool, so claim `.data 0x804D2880-0x804D2AE0` and define every object in it: the version string as a global `char lbl_804D2880[]` first, `static VITiming timing[10]` (0x26-byte entries, ac-decomp's `VITiming` layout; this game has 10, not 8), then a non-`static` `taps` array (a static that nothing references would be stripped). Split the blob in `symbols.txt` to match (`lbl_804D2880` 0x44 string, `timing_804D28C4`, `taps_804D2A40`). `getTiming` now lives in `VIInit.c` (the SDK `vi.c` from `getTiming` to `VIConfigurePan`), which defines this pool and the `.bss` one (see the pooled-struct note below). Decode the case list from the jump table (cases 6/7/10-15/18/19/22/23/25 are default).
- **The same trick works when the 8-aligned objects in front of the table belong to a *different*, still-unsplit function, but they need `#pragma force_active on` (`VIGetTvFormat`, `0x8018992C`).** Its table `@724` (`0x804D2C34`, 4-mod-8) follows VIConfigure's seven `OSReport` strings (`0x804D2AE0`, 8-aligned). Claim `.data 0x804D2AE0-0x804D2C50` and define the strings as global `char lbl_...[]` arrays in `VIGetTvFormat.c` (MWCC keeps declaration order, pads each string to 4, and puts the table last). mwld then dead-strips the strings, because VIConfigure's asm reaches them as `lbl_804D2880`+offset, never by symbol, so wrap them in `#pragma force_active on` / `reset`. Split the blob into per-string symbols in `symbols.txt`. VIConfigure's asm now sits in `VIInit.c`; to finish `vi.c`, extend that unit over `VIFlush` through `__VIGetCurrentPosition` (`0x8018960C-0x80189C10`) and move the strings into it.
- **Claiming a function whose caller is already in the same unit can make MWCC inline it** (`-inline auto`): the caller shrinks (`AlarmHandler_80184B70` 0x44 -> 0x40), every later unit shifts 4 bytes, and `main.dol` breaks with ~48% of bytes differing even though each function reports 100% on its own. Wrap the definition in `#pragma dont_inline on` / `reset`. If the caller loads an argument (`lwz r3,executing`) the original callee takes an unused parameter; keep it in the prototype (`stateReadingID`, `0x80184C80`).
- **String literals for a unit live in three places -- claim them all with the unit or `main.dol` shifts:** `__fstLoad` (`0x80186B58`) has its long `OSReport` strings pooled in `.data` (`0x804D2810-0x804D2880`, 8-aligned, addressed off one `r31` base) but the 1-3 char ones (`"\n"`, `"OFF"`, `"ON"`) in `.sdata` (`0x8066C470-0x8066C480`, `li rX, lit@sda21`). Claim `.data`, `.sdata`, and the `.bss` of its `static` locals in `splits.txt`, and write the literals inline. The function-local `static block` (`block$16`) and file-static `bb2Buf` become plain `static` arrays in the unit. The unused `switch` on the drive state in ac-decomp's version compiles to nothing (empty loop `bne`), so omit it.
- **A small data object you define without `const` lands in `.sdata`, not `.sdata2`, even when `symbols.txt`/`splits.txt` say `.sdata2`:** MWCC routes small non-`const` globals to `.sdata` and small `const` globals (under the small-const threshold) to `.sdata2` purely from the C qualifier, regardless of which section the claim targets. The symptom is `.sdata` growing by the object's size and `.sdata2` shrinking by the same, `main.dol` breaking by that many bytes with thousands of scattered `text` diffs from every `r13` displacement after it shifting. Fix: add `const` to every scalar/array meant for a `.sdata2` claim (`KernelTanfT0`..`T12`, `0x8066FE10`, `__kernel_tanf.c`).
- **A unit that owns a `.rodata.1` range has to declare the section and pin the definition to it: `#pragma section R ".rodata.1"` plus `__declspec(section ".rodata.1")` on the object.** Ordinary `const` data goes to `.sdata2` when it is under MWCC's small-const threshold (an 8-byte double is) and to `.rodata` otherwise, both the wrong output section, and `__declspec` on its own fails with `unknown section name '.rodata.1'` because the name must be declared first. The pragma takes an access permission (`R`), not an object type: `const`, `data` and `RO` are all rejected. Unlike `.sdata2`, these `@ha`/`@l` relocations survive `bake-sda`, so a unit whose own code references the data needs no `#pragma force_active` (`Fp2UnsignedTwoTo31Const`, `0x8049C1C8`, `__cvt_fp2unsigned.c`). The `__declspec` also overrides the zero-fold below, so an explicit-zero scalar (`const double FloorZeroConst = 0.0;`) stays in `.rodata.1` instead of going to `.sbss`, and no array/struct wrapper is needed (`floor.c`, `0x8049C800`). A `.rodata.1` claim may start 4-mod-8, unlike the `.data`/`.sdata`/`.sbss` claims below: dtk gives the section `align:4` and a lone string object carries no higher alignment, so claim the range as-is instead of widening it back to an 8-aligned start (`UngetcErrorStr`, `0x8049C8DC`, `ungetc.c`, claimed straight after the 8-aligned `__ieee754_log10` pool's 2-byte neighbour).
- **Two separate top-level `const` globals placed in the same unit's `.rodata.1` always start the second one on a 4-byte boundary, even when it's given an explicit size or `__attribute__((aligned(1)))`.** This doesn't match an original layout where two tables were packed with zero gap between them (Newlib `asctime_r`'s `day_name[7][3]`/`mon_name[12][3]`, 21+36 bytes, no padding). Fix: merge the two into one array/object so there's no boundary to align, and reach the inner table by offset arithmetic on the symbol, not on the `@ha`/`@l` result — `lis rX, (Symbol+0xNN)@ha` / `addi rX,rX,(Symbol+0xNN)@l` (`Symbol@l+0xNN` is a syntax error; the offset must be inside the parens). Give it an explicit size (`const char AsctimeNames[57] = "SunMon...Dec";`): `[]` keeps the literal's NUL, which the original doesn't have, and objdiff scores the section below 100% even though `main.dol` matches. Example: `AsctimeNames` (`0x8049C420`, `asctime_r.c`), one 57-byte array holding both tables, with the month lookup at `(AsctimeNames+0x15)@ha`/`@l`.
- **A claimed literal pool is in MWCC's *first-use* order, not the reference's declaration order, and it holds compiler-generated constants the reference has no name for.** When defining a claimed `.rodata.1`/`.sdata2`/`.sdata` pool for an `asm` function, order the definitions by where each address is first loaded in the disassembly and look up every slot's bytes rather than transcribing the reference's `static const` list. fdlibm's `e_log10.c` declares `two54, ivln10, log10_2hi, log10_2lo, zero` but the pool is `-two54/zero` (folded), `zero`, `two54`, then the int-to-double magic `0x4330000080000000` for `(double)k`, then `log10_2lo, ivln10, log10_2hi` (`__ieee754_log10.c`, `0x8049C8A0`).

- **A pool slot whose value has no C literal (`+-inf`, NaN) is defined as a union whose first member is the bit pattern**, which keeps the 8-byte alignment a bare `unsigned long w[2]` would lose (`Log10NegInfConst`, `0x8049C8A0`):

  ```c
  __declspec(section ".rodata.1") const union { unsigned long w[2]; double d; }
      Log10NegInfConst = {{0xFFF00000, 0x00000000}};
  ```

- **Newlib's `vfprintf`-family `blanks`/`zeroes` pad buffers are plain `char[16]` arrays, not C strings** (no NUL terminator, back-to-back in `.rodata.1`): define them as `const char Name[16] = {' ', ' ', ...}` / `{'0', '0', ...}`, not `const char Name[] = " "` (a string literal appends a NUL that isn't in the original byte stream and desyncs everything after it). The adjacent hex-digit tables and error string (`"0123456789abcdef"`, `"(null)"`, `"bug in vfprintf: bad base"`) *are* real C strings and take ordinary string-literal initializers (`VfiBlanksConst`/`VfiZeroesConst`, `0x8049C610`, `_vfiprintf_r.c`; `_vfprintf_r.c`'s own copy at `0x8049C580` is the same shape).
- **Claiming a data range whose owning unit sits far later in link order still works: no `link_order_callback` is needed.** dtk re-slots the leftover `auto_<n>_<addr>_<section>.o` objects around the claiming unit when it regenerates `config.json`, so the output section keeps address order even though link order otherwise follows `.text`. Claim the range and let `main.dol: OK` be the check (`SNUnknownDvdCmdMsg`, `.rodata.1` `0x8049C1D0`, owned by `SN/fn_8016C148.c` at `.text` `0x8016C148`).

  **Doesn't help** for a lone scalar carved out of the *middle* of one large contiguous still-unclaimed pool whose readers are scattered across nearly the entire link order (e.g. a run of `.sbss` globals touched by units from opposite ends of the project): splitting it into a claimed slice plus two leftover auto-objects can give the two halves mutually conflicting link-order requirements, and `dtk dol split` rejects it outright with a `Cyclic dependency encountered while resolving link order` error naming most of the project's units, regardless of whether the split uses the `common` attribute. No source-side fix; the range needs a different approach entirely, such as claiming the whole surrounding pool as one unit instead of a 4-byte slice (`errno`, `.sbss` `0x8066FB30`, would-be owner `Runtime.PPCEABI.H/_close_r.c`).
- **`.sdata2` symbols in compiled C are fine:** the `sda2_via_r13` option bakes those accesses as `r13` offsets (see [`baseline.md`](baseline.md#small-data-r13-problem)), so write them as ordinary C.<br />
  If `Range Error for small data relocation` appears, check that `build.ninja` was generated with the fork's `dtk-dev` and that `build/GVLE69/sda_bake.json` exists.
- **Struct fields of a pooled `.bss` static reached through a pointer/extern lose MWCC's hoisted address temps: `sth rX,0x106(base)` followed by `addi r11,base,0x106` (reused later as `lhz rY,0(r11)`) needs real defined objects.** A `u8*` cast base also makes every store alias the unit's `.sbss` globals: in `VIInit` (`0x801880D8`) `CurrTiming` was reloaded after each `HorVer` store, so the original's `lwz r4,CurrTiming` / `lhzu r0,2(r4)` (one `&CurrTiming->acv` temp) never formed. With `regs`/`shdwRegs`/`HorVer` *and* the `.data` pool (`timing`, `taps`) defined in the unit, ac-decomp's plain source matches; an extern for either pool swaps the two base registers whatever the declaration order. Define the *whole* pool including the neighbouring object that precedes the struct, or the base and every offset shift. A hand-made field pointer (`unsigned long* p = &scb->offset;`) gets the saved-register temp but schedules it after the first load: the original's `addi r30,r31,0x40` *before* `lwz r0,0x40(r31)` came only from plain `Scb.offset` with `Scb` defined in the unit. When a neighbouring unit already claims the object's `.bss`, merge the contiguous units into it (`UnlockSram`, `0x8017F2E4`, joined `__OSInitSram.c` with `__OSLockSram`/`Ex`, whose code is unchanged by the pooling).
- **A truly unreferenced filler object you define in a claimed `.sdata`/`.sbss` range (no relocation anywhere points at it) is dead-stripped by the linker even as a non-`const` array, even pinned with a discarded `(void)obj;` read: the symbol vanishes from the final link entirely and every later `r13`-relative displacement in the *whole ROM* shifts by the object's size (visible as thousands of scattered one-byte `text` diffs at a constant delta, `main.dol` size unchanged).** The `(void)obj;` pinning trick (see the pooled-`.bss` note above) only fixes *layout order* among objects the linker keeps; it does not stop this dead-stripping. If the byte range you actually need to define starts on its own legal (8-aligned, per the `.sdata`/`.sbss`-start rule above) address, don't widen backward to absorb the leading unreferenced filler at all -- leave it unclaimed for dtk to keep auto-emitting, which carries no dead-strip risk since it never goes through the compiler/linker as a real symbol. Example: `dvdfs.c`'s `.sdata` claim needs only `lbl_8066C408` (`"dvdfs.c"`, already 8-aligned at `0x8066C408`); the preceding unreferenced zero word at `0x8066C404` stays unclaimed.
- **Several `scope:global` `.sbss`/`.sdata` scalars defined together in one unit, all genuinely read somewhere in that unit's own code, can still lay out in the *reverse* of their C declaration order, not first-use order.** Simple statement-order first-use prediction (scanning each function top to bottom for the first mention of each global) does not reliably predict the real order either -- two scalars first touched in the same statement's expression (an assignment computed from one and stored into the other) can come out in either order relative to that prediction. When several such globals stall on relative offsets with every instruction otherwise identical, try declaring them in the exact reverse of the address order you need and check the linked addresses (`readelf -s` on `build/GVLE69/main.elf`) rather than reasoning further about the heuristic (`dvdfs.c`'s `BootInfo_8066F2A0`/`FstStart`/`FstStringStart`/`MaxEntryNum`/`currentDirectory`/`__DVDLongFileNameFlag`/`__DVDThreadQueue`, `.sbss` `0x8066F2A0-0x8066F2C0`).

- **Linker-generated addresses (`_stack_addr`, `_stack_end`, `__ArenaLo`, `__ArenaHi`) are pinned in `config/GVLE69/ldscript.lcf`.** dtk only relocates `lis`/`addi` pairs to them once it knows their values, which here came from dtk-dev's `OSInit` signature; from then on crt0, `__OSThreadInit` and `OSInit` link against the LCF. The stock template formulas are wrong for this game: the original `_stack_end` is `0x806709A0` (0x20 past `.sdata2`) and `__ArenaLo` is `0x806809C0` (0x20 above the stack top, no `0x2000` debugger stack). If `main.dol` differs only in `lis`/`addi` pairs near `0x8068`/`0x8067`, check these first. `__ArenaHi` (`0x81780000`) comes through `$ARENAHI`.
- **An `asm` helper made of `entry` labels needs a `type:function` symbol in `symbols.txt` at its start:** dtk left `0x8017B230` as the `__OSDBINTEND` label only, so `__OSDBJump` had no target counterpart, and objdiff tagged a later `mr r4,r31` (a pointer to the entry) on our side only. Add `__OSDBJump = .text:0x8017B230; // type:function size:0x4 scope:local`.

## General tactics

- Comments and whitespace do not affect output, except for `__LINE__`/`__FILE__` and whitespace inside string literals.
- Register allocation differences usually indicate a different expression shape or variable lifetime. Try reordering locals or introducing/removing a temporary.
- **A loop-condition load `while ((count = sem->count) <= 0)` where the original reloads `sem->count` after the loop (`lwz r30` in the condition, a fresh `lwz r4` for the decrement) and ours reuses `count`: make the field `volatile`.** MWCC CSEs the exit block's load against the condition's; `volatile s32 count;` in the struct stops that and keeps the same `lwz`/`subi`/`stw` decrement. Restructuring the loop (`goto`, `while (1)`, a preloaded `count`) and `opt_common_subs off` don't help (`OSWaitSemaphore`, `0x804043A4`).
- **`old = p->f++;` gives the old value in a scratch register plus a trailing `addi rSaved,rScratch,0` copy, where the original loads it straight into the saved register that survives a later call:** write `old = p->f; p->f = old + 1;` (`OSSignalSemaphore`, `0x80404468`).
- **The reverse of the rule above: a saved return value that's also compared/used before a later call, where two separate statements (`count = sem->count; ret = count;`) collapse to one register (load straight into the saved register, no copy), but the original keeps a scratch register plus a trailing `addi rSaved,rScratch,0` copy.** MWCC copy-propagates two same-valued locals into one register when they're written as separate statements; a chained assignment (`ret = count = sem->count;`) keeps them distinct and reproduces the copy (`OSTryWaitSemaphore`, `0x80404414`).
- **Keep no-op statements and "redundant" locals from the reference source; they change register allocation.** ac-decomp's `GXSetTexCopyDst` (`0x801929BC`) has `peTexFmtH = (peTexFmt >> 3) & 1; !peTexFmt;` before the insert. Both emit nothing, but without them the argument copies before the `bl` come out in a different order and `__GXData` lands in r6 instead of r4. Paste the reference body verbatim before reshaping it.
- **Two params in swapped saved registers, or an extra `addi rX,rY,0` pointer copy that becomes a loop's store base while the original pointer is used after the loop: the SDK used aliasing locals.** Copy the param into a typed local at the top (`bootInfo2 = (char*)addr;`) and use only the local, and keep the byte cursor and the typed array separate (`ptr -= n * 4; list = (char**)ptr; ... list[i] = ...; ptr -= 4;`) rather than one `char** newArgv` stepped with `-= n` (`PackArgs`, `0x8017D228`; each local alone fixed half the diff).
- Instruction scheduling differences often come from the compiler hoisting a constant. Match the source structure rather than the instruction order directly.
- If you're stuck around 95% on register choice, [decomp-permuter](https://github.com/simonlindholm/decomp-permuter) can brute-force equivalent C forms.
- **A hardware-register store where the original is `lis`/`addi r3,r3,0x2000` then `sth r0,2(r3)` (base register with a separate offset)** can't be written in C: every form of `__VIRegs[1] = 0` (address-declared array, cast local, `register`, `vi + 1`) folds the offset into the store (`sth 0x2002(r3)`). Write it as `asm` (`__OSDoHotReset`, `fn_8017A6EC`).
- **Loads that stay below an earlier store to a different global mean those globals are `volatile`.** MWCC reorders ordinary global loads above stores to other globals freely. If the original keeps a `lwz` pinned after a `stw` to an unrelated global (e.g. `lwz executing` after `stw ResumeFromHere`), `volatile` is the fix. It has to go on *all* the involved globals at once; single ones don't help. In `dvd.c` these are `Canceling` (`lbl_8066F2E0`), `ResumeFromHere` and `NumInternalRetry` (later-SDK declarations; `cbForStateGettingError`'s inlined `CheckCancel`). To test a hypothesis like this, compile another function that inlines the same helper (here `cbForStateCheckID3`) and diff it too.
- **Two volatile registers swapped with everything else exact: check the SDK type of every global involved, `int` vs `long` included.** `int` and `long` are both 32 bits, but MWCC colors the registers differently. The five PAD callbacks (`PADOriginCallback`, `PADProbeCallback`, `PADTypeAndStatusCallback`, `PADReset`, `PADRecalibrate`) had an `r4`/`r5` swap in the inlined `DoReset` until `ResettingChan` (`lbl_8066C49C`) went from `extern int` to `extern long` (the SDK has `static s32 ResettingChan`, and `s32` is `long`). `u32`, `volatile`, locals, statement order, inline-vs-static and declaring it `static` in the TU did nothing. The same holds for a *local* loop counter: `long chan` in `PADRead` (`0x8018A7FC`) swapped two hoisted-invariant saved registers (the `0x80000000` constant and a callback address, r30/r31) that `int chan` fixed; 400 declaration-order permutations did nothing. The `s32` typedef itself counts: with `typedef int s32` (the SDK's is `long`), `VIConfigurePan` (`0x80189278`) stalled at 94.43% with rotated saved registers and no `subf` in the true arm of each `MIN`/`MAX(x, 0)` (the original recomputes `subf.` / `ble` / `subf`), and `typedef long s32` matched it. Check a unit's typedefs first.
- **Inlined `EXIClearInterrupts` in an interrupt handler with an `OSContext` local on the stack (`EXIIntrruptHandler`, `0x80194CEC`): `#pragma scheduling off`, a `static inline` copy of the helper, and declare the context as `long long ctx[0x2c8 / 8]`.** A `char[0x2c8]` local is 4-aligned (context at `0x14(r1)`, frame `-0x2f0`); the real `OSContext` is 8-aligned (`0x18(r1)`, `-0x2f8`). With scheduling on, saved-register order is wrong (chan/context/callback rotated). The handler must be non-`static` (`scope:global` in `symbols.txt`) if `EXIInit` still references it. The same shape fits `EXTIntrruptHandler` (`0x80194FCC`, no inline helper; the `0x500000U` literal must be unsigned or the shift becomes `sraw`) and `TCIntrruptHandler` (`0x80194DB4`, plus a `static inline` copy of `CompleteTransfer`, whose `immBuf` byte-store loop unrolls by 8 in the original too, and `EXIClearInterruptsI(chan, 0, 1, 0)`); `__OSMaskInterrupts(0x80000000U >> interrupt)` takes the raw `short`. The EXI control regs are `__EXIRegs[5 * chan + 3]` (`0xC`/`0x20`/`0x34` off the base), not stride 4.
- **Pooled `.data` owned by another (asm) unit, where a struct-pointer local gets the base right but the wrong reload shape (`CompleteTransfer`, `0x80181764`): take `u8* b = lbl_804D1B78;` (the pool's first object) and reach each object as `((SIControl*)(b + 0x44))->x` / `((u32*)(b + 0x58))[i]`.** The original hoists `addi r6,r31,0x4c` (`&Si.inputBytes`) for the second read; an `extern SIData` struct with a `SIData* d` local, a `u32*` local, or macros on the extern itself all miss it.
