# Confirmed Non-Matches

Functions claimed as `NonMatching`, with what has already been tried. Don't re-guess these. When a unit flips to `Matching`, delete its entry and move any general lesson to [`matching_notes.md`](matching_notes.md).

Checked across every entry below, none of these helped: compiler versions `GC/1.0` to `2.0` (`1.2.5n` is best or tied everywhere), `-O4,s`/`-O4`/`-O3`/`-O2`, `-inline off`, `-use_lmw_stmw on`, and `#pragma scheduling off`/`peephole off`/both.

- `__GXSetVCD` (`0x8018C3FC`, `Dolphin/gx/__GXSetVCD.c`): `NonMatching`, 99.79% (one register). ac-decomp's `__GXSetVCD` with the *later-SDK* `__GXXfVtxSpecs` as a `static inline` (a plain `static` stays a `bl`): `nCols = (u32)(33 - __cntlzw(GET_REG_FIELD(vcdLo, 4, 13))) / 2`, `nTex = (u32)(33 - __cntlzw(GET_REG_FIELD(vcdHi, 16, 0))) / 2`, `reg = nCols | (nNrm << 2) | (nTex << 4)`; not ac-decomp's per-field `? 1 : 0` sums (those give branches). Cast the `33 - __cntlzw` to `u32` or you get `srawi`/`addze`.
  - Remaining: the original's tex `clrlwi r3,r3,16` is in place (`cntlzw r0,r3`); ours is `clrlwi r0,r3,16` / `cntlzw r0,r0`.
  - No effect: `(u16)` cast or `& 0xFFFF` instead of `GET_REG_FIELD`, `__cntlzw((u16)x)` (94%), inline `GET_REG_FIELD` in the `__cntlzw` argument, `nTex = nTex` no-op, extra unused locals, local declaration order, `nCols = 0` initialiser, `(33 - x) >> 1`, `32 - x + 1`, reusing one temp for both fields (83%). Computing `nTex` before `nCols`, or moving the `vcdHi` read earlier, is much worse (81-92%).
