# Confirmed Non-Matches

Functions claimed as `NonMatching`, with what has already been tried. Don't re-guess these. When a unit flips to `Matching`, delete its entry and move any general lesson to [`matching_notes.md`](matching_notes.md).

Checked across every entry below, none of these helped: compiler versions `GC/1.0` to `2.0` (`1.2.5n` is best or tied everywhere), `-O4,s`/`-O4`/`-O3`/`-O2`, `-inline off`, `-use_lmw_stmw on`, and `#pragma scheduling off`/`peephole off`/both.

- `GXSetTexCopyDst` (`0x801929BC`, `Dolphin/gx/GXSetTexCopyDst.c`): `NonMatching`, 94.41%. Needs `fmt` as `int`, `u16` width/height on the `__GetImageTileCount` prototype, a direct `__rlwimi(cpTex, peTexFmt, 0, 28, 28)`, a `u8 mipmap` param, `extern ... * const __GXData` with direct access up to the call, and a `gx` local reloaded after it.
  - Remaining: the original emits the two argument copies as `addi r5,r7,0` then `addi r4,r8,0`, so `__GXData` can reuse the still-free r4; ours emits them in the opposite order and has to put `__GXData` in r6. No effect: `u32`/`int` `wd`/`ht`, `w`/`h` locals, a `g` local for the `cpTexZ`/`cpTex` block, moving `peTexFmt &= 7`, `#pragma scheduling off` (42%), `#pragma peephole off` (32%).
- `OSCreateThread` (`0x8018037C`, `Dolphin/os/OSCreateThread.c`): `NonMatching`, 99.51%. Two gaps. (1) Frame `-0x48` vs `-0x50`: the 7 params already cost 32 bytes and the unrolled `i` loop 8 (see the frame-size note in [`matching_notes.md`](matching_notes.md)). Two never-assigned `u32` locals (in any position) or an unused `u64` close it, but no SDK source is known to declare them, so that is padding. (2) The original passes `&thread->context` as `addi r3,r31,0`; ours is `mr r3,r31` (a peephole-pass difference, see the `addi`/`mr` note in [`matching_notes.md`](matching_notes.md)). With the two locals in, only that copy differs. No effect on the copy: casts, `+ 0`, `(OSContext*)thread`, a `ctx` local, an inline wrapper around the `OSInitContext` call, an inline `RoundDown8` for `sp`, `u32*` `sp`, call order, `#pragma peephole off` (87%), chained `fpr`/`psf` store (73%). No effect on either gap: `OSInitThreadQueue` as an inline for `queueJoin`/`queueMutex`, `prev` at function scope, the enqueue as an inline helper, `f64` `fpr`/`psf` with `*(u64*)&` stores, `u32 i`, a `stackEnd` local, a `c = &thread->context` loop base, reordering or reshaping the `sp` setup and the two `((u32*)sp)[n] = 0` stores. Two separate loops change the code (640 bytes).
- `GXLoadLightObjImm` (`0x8018D8D4`, `Dolphin/gx/GXLoadLightObjImm.c`): `NonMatching`, 92.42%. This game's version takes `light` as a bitmask (`cntlzw`, `31 - n`, `& 7`, `<< 4`, `+ 0x600`), not ac-decomp's `GXLightID` switch. The zero/color/`psq_l`/`stw`/`psq_st` run only inlines via a `static inline` helper with an `asm {}` block (a `static asm` function stays a `bl`).
  - Remaining: the original keeps the `cntlzw` chain in r0, the fifo pointer in r4, and the first `stw` of the address is `stwu` (which also sets the pointer). Ours puts the chain in r4/r5 and emits a plain `stw` plus an `addi r5,r7,-0x8000`. Writing `*fifo = ...` through a `volatile u32*` local produces the `stwu` but shifts registers (92.4% either way). No effect: `idx` temp vs inline expression, `fifo` local ordering, `* const __GXData`, declare-at-address `GXWGFifo`.
- `UnlockSram` (`0x8017F2E4`, `Dolphin/os/OSUnlockSram.c`, static `UnlockSram` in the SDK's `OSRtc.c`, global here because `OSGetSoundMode`/`OSSetGbsMode`/... call it): `NonMatching`, 98.07% (size 0x33C exact, 4 diff lines). ac-decomp's body plus the game's gbs sanitise (`if (Scb.offset <= 0x14)`, `(mode & 0x7C00) == 0x5000 || (mode & 0xC0) == 0xC0` -> `gbsMode = 0`) and a `static inline` copy of `WriteSram` (the unit, not the `WriteSram.c` one, inlines it).
  - What got it there: `SramControlBlock* scb = &Scb;` at the top (gives the `lis`/`addi r31` base up front and the `stmw r27`), `unsigned long mode` (a `u16` gives `cmpwi`, the original is `cmplwi`), an `OSSramEx*` local for the `sth 0x28(r4)` store, and a nested `{ unsigned long* poff = &scb->offset; ... }` block after the checksum loop for the `addi r30,r31,0x40` that the original keeps live across the `EXI*` calls (C89: the declaration must open a block; at function scope the `addi` moves to the prologue, 12 diff lines).
  - Remaining: the original schedules `addi r30,r31,0x40` before `lwz r0,0x40(r31)` and `addi r4,r31,0x14` before `lhz r3,0x3c(r31)`; ours puts each load first.
  - No effect: `poff` read/compare via `*poff` or `scb->offset`, `> `/`<` operand order, `const`/`register` qualifiers, split declaration and assignment of `mode`, `#pragma opt_lifetimes off`. Worse: `&Scb.offset` (8), `volatile` `poff` (18), `#pragma scheduling off` (64), `peephole off` (70), `opt_common_subs`/`opt_propagation off` (12).
- `PackArgs` (`0x8017D228`, `Dolphin/os/PackArgs.c`): `NonMatching`, 96.22% (size 388 vs 392; 17 diff lines, mostly register renumbering). Confirmed SDK `OSExec.c` shape (MWCC, not GCC): `memset(addr,0,0x2000)`; `if (argc == 0) addr[2] = 0; else {...}` with a shared `return 1` at the end (an early `return 1` in the `argc == 0` arm duplicates the `li r3,1`); `while (--argc >= 0)` using `argv[argc]` indexing (this gives the original's `subic.`/`subi` pair in the loop condition; `argc` doubles as the counter, `numArgs = argc` is the kept copy); `newArgv = (char**)((char*)addr + ((ptr - (char*)addr) & ~3)); newArgv -= numArgs + 1;`; `u32 n` copy loop (unsigned `cmplwi`, unrolled by 8) `newArgv[n] = argv[n]`; `newArgv[-1] = numArgs; addr[2] = (newArgv - 1) - addr`. Declaring `u32 n` last (`numArgs, ptr, newArgv, n`) is best.
  - Remaining: (1) `addr`/`argv` land in swapped saved registers (original `addr` r30, `argv` r29; ours the reverse). (2) The original holds a separate destination-pointer copy (`addi r5,r6,0`, then `addi r4,r5,0` for the unrolled loop, `add r5,r5,r0` in the remainder), while ours addresses the remainder off `newArgv` (`add r5,r6,r0`). (3) The original computes `numArgs + 1` (`addi r3,r31,1`) *after* `subf r0,addr,ptr`; ours hoists it above.
  - No effect / worse: all 24 declaration orders of the four locals x {`newArgv[n]`, `dst = newArgv; dst[n]`, `*dst++`} (best 17 diff lines); explicit `p = argv + argc` pointer in the first loop (`lwzu`, no `subi` in the condition); `i = argc; while (i-- > 0)` (drops to 87%); `cnt = numArgs + 1` local (worse); `char* addr`, `u32* hdr` local, `av = argv` local; one-expression `newArgv` (93.9%).
