# Confirmed Non-Matches

Functions claimed as `NonMatching`, with what has already been tried. Don't re-guess these. When a unit flips to `Matching`, delete its entry and move any general lesson to [`matching_notes.md`](matching_notes.md).

Checked across every entry below, none of these helped: compiler versions `GC/1.0` to `2.0` (`1.2.5n` is best or tied everywhere), `-O4,s`/`-O4`/`-O3`/`-O2`, `-inline off`, `-use_lmw_stmw on`, and `#pragma scheduling off`/`peephole off`/both.

- `__GXAbort` (`0x80192190`, `Dolphin/gx/__GXAbort.c`): `NonMatching`, 98.85% (size 368 vs 364; 2 diff lines). Body is an older GX abort: `if (__GXData->unk5AA && GXGetGPFifo())` wait loop on a 32-bit MEM counter (`__memReg[0x27]`/`[0x28]`, stable-read like `__GXReadCPCounterU32`, `__GXAbortWait(32)` between reads until two reads agree), then `__PIRegs[6] = 1; wait(200); = 0; wait(20)` (`volatile u32 __PIRegs[0x20] : 0xCC003000;`, `__GXAbortWait` as ac-decomp). Everything matches except the outer loop tail.
  - Remaining: the original ends the retry loop with `cmplw r0,r27` / `mr r27,r0` / `bne top` (fall through to exit, `prev` stays in r27); ours emits `cmplw` / `mr` / `beq exit` / `b top`, or, with a separate `old`, an extra `addi r4,r27,0` copy. The best form is `old = prev; prev = cur;} while (cur != old)` (98.85%, one extra copy).
  - No effect: `while (1)`/`for (;;)` with `if (cur == prev) break; prev = cur;`, `continue`/`break` inversion, `goto`, `for (;; prev = cur)`, `&&`/`||`/ternary/comma conditions, `do {prev = cur; ...} while (cur != prev)` (copy lands at the loop head, 94%). A `changed = cur != prev;` flag gives `subf`/`subic`/`subfe.` instead of `cmplw`. `peephole off` (67%), `scheduling off` (83%), `optimize_for_size` (no change). An unused extra local adds 8 to the frame (`-0x30` vs `-0x28`).
- `VIConfigurePan` (`0x80189278`, `Dolphin/vi/VIConfigurePan.c`): `NonMatching`, 94.43%. Port of ac-decomp's `VIConfigurePan` with `AdjustPosition`/`setScalingRegs`/`setPicConfig` as `static inline`s; the instruction stream is identical modulo register numbers plus five `subf` (below), and every immediate/reloc matches.
  - What got it there: the unit claims the whole VI `.bss` pool (`0x8057D418-0x8057D560`) and *defines* `lbl_8057D418` (`regs`, `u16[59]`), `shdwRegs` (`u16[59]`, `0x8057D48E`) and `HorVer` (`0x8057D508`, the `SomeVIStruct` from `setFbbRegs.c`), pinned in that order with `(void)` at the top (see the pooled-`.bss` note in [`matching_notes.md`](matching_notes.md)). Extern-pointer forms (`u16 regs[]` plus a `HorVer` macro cast, or one `VIData` extern struct with a `d` base local passed to the helpers) lose the `addi rX,base,0x106`-style address temps (`&HorVer.PanPosX` etc.) and land at 71-85%.
  - Remaining: the original recomputes the subtract in the true arm of each of the five `MIN`/`MAX(x, 0)` sites (`subf. r26,r7,r25` / `ble` / `subf r25,r7,r25`); ours reuses the `subf.` result (no arm instruction). The saved registers are also rotated: original `r27` `&DispSizeY`, `r28` `tm`, `r29` base, `r30` `enabled`, `r31` `&AdjustedDispPosY`; ours `r27`/`r28`/`r29`/`r30`/`r31` = `&AdjustedDispPosY`/`&DispSizeY`/`tm`/base/`enabled`. The recompute is what MWCC does when the arm result is coalesced onto a dead source register (reproducible in a scratch TU for the `MAX` site), so it is probably a register-allocation consequence, not source shape.
  - No effect: `MAX`/`MIN` as `>=`/`<=`, swapped operands, `+ 0`, `(b) + ((a) - (b))`; `-(-(a))` (folded); `#pragma opt_common_subs off` (81%, whole function); `static` for the three `.bss` objects; `enabled`/`tm` declaration order (4 orders); `(void)` pins after `OSDisableInterrupts`; `tm->acv` via `HorVer.timing->acv`, an `acv` local, `tm` assigned before/after; `coeff`/`frac` declaration order; a trailing `(void)tm`.
